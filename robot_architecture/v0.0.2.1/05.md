# Data Contracts

> *"Subsystems should share meaning, not implementation."*

---

# 5.1 Purpose

Chapter 04 defined how information moves through the RoBoT architecture.

This chapter defines the structured information exchanged during that movement.

A cognitive architecture becomes difficult to evolve when every subsystem creates its own interpretation of shared information.

One subsystem may call something an event.

Another may call it an observation.

Another may store the same information as a database record.

Another may pass it as an unstructured string.

Over time, these differences create hidden dependencies between systems.

RoBoT therefore establishes canonical data contracts.

A data contract defines the meaning, structure, ownership, and expected behavior of information exchanged between subsystems without requiring those subsystems to share their internal implementation.

The contract layer provides:

* stable subsystem boundaries

* predictable communication

* explicit ownership

* version compatibility

* serialization

* validation

* traceability

* replayability

* testing

* implementation independence

The goal is not to create one enormous universal data structure.

The goal is to create a small, coherent vocabulary that allows independent systems to communicate without becoming dependent on one another's internals.

---

# 5.2 What a Data Contract Is

A data contract defines an agreement between systems.

Conceptually:

```text

Producer

   │

   │  Contract

   ▼

Consumer

```

The producer guarantees that the information conforms to the contract.

The consumer agrees to interpret the information according to that contract.

The producer may change its internal implementation without requiring the consumer to understand those internal changes.

For example:

```text

Memory Engine

      │

      │ MemoryQuery

      ▼

Retrieval Interface

      │

      ▼

Memory Results

```

The planner does not need to know whether the Memory Engine uses:

* SQLite

* PostgreSQL

* a vector database

* a graph database

* flat files

* an in-memory cache

* multiple storage systems

The contract remains the boundary.

---

# 5.3 Contract Design Principles

All RoBoT data contracts should follow a common set of principles.

## 5.3.1 Explicit

The meaning of every field should be understandable.

Avoid fields whose meaning depends entirely on undocumented behavior.

---

## 5.3.2 Minimal

Contracts should contain information necessary for communication.

Internal implementation details should not be exposed merely because they are available.

A contract should not become a dumping ground for every field a subsystem happens to possess.

---

## 5.3.3 Versioned

Contracts must be versionable.

A change to a contract may affect multiple subsystems, stored records, logs, and historical data.

Schema evolution must therefore be deliberate.

---

## 5.3.4 Traceable

Important objects should be identifiable and correlatable.

Where practical, a contract should allow the architecture to determine:

* where information originated

* when it was created

* which operation produced it

* which task it belongs to

* which objects it relates to

---

## 5.3.5 Serializable

Contracts should support serialization where practical.

This allows the same conceptual object to be:

* stored

* transmitted

* logged

* replayed

* tested

* inspected

* archived

---

## 5.3.6 Validatable

A receiving subsystem should be able to determine whether an incoming object satisfies the contract.

Invalid data should be rejected or explicitly marked rather than silently accepted.

---

## 5.3.7 Implementation Independent

Contracts describe **what information means**, not **how a subsystem implements it**.

A contract should not expose database-specific structures, model-specific internals, or language-specific implementation details unless those details are themselves part of the intended interface.

---

## 5.3.8 Immutable by Default

Published cognitive objects should generally be treated as immutable.

When information changes, the architecture should prefer:

```text

Original Object

      ↓

New Version / Update

```

rather than silently changing historical data.

This is particularly important for:

* observations

* decisions

* execution results

* reflections

* experiences

* audit records

---

# 5.4 Contract Categories

RoBoT contracts can be divided into several broad categories.

| Category | Purpose |

| --------------------- | ------------------------------------------ |

| **Input Contracts** | Bring information into a subsystem |

| **Query Contracts** | Request information |

| **Result Contracts** | Return information |

| **State Contracts** | Represent current state |

| **Action Contracts** | Request authorized operations |

| **Event Contracts** | Report something that happened |

| **Cognitive Objects** | Represent meaningful cognitive information |

| **Update Contracts** | Propose changes to persistent state |

| **Control Contracts** | Manage runtime and subsystem behavior |

This distinction prevents every message from being treated as the same kind of object.

# 5.6 Common Contract Metadata

Where applicable, RoBoT contracts should share common metadata.

A conceptual base may include:

```text

ContractMetadata

----------------

id

schema\_version

created\_at

producer

correlation\_id

parent\_id

source

provenance

confidence

priority

metadata

```

Not every contract requires every field.

The purpose of common metadata is to establish consistent conventions across the architecture.

---

# 5.7 Identity

Every significant contract should have a stable identifier.

Identifiers allow systems to distinguish:

* one observation from another

* one plan from another

* one execution from another

* one experience from another

* one version from another

Identifiers also enable relationships between objects.

For example:

```text

Goal

  id = G-1042



Plan

  id = P-881

  goal\_id = G-1042



Decision

  id = D-391

  plan\_id = P-881



Execution

  id = X-775

  decision\_id = D-391

```

This creates a traceable chain without requiring every object to contain the complete history of the task.

---

# 5.8 Correlation

A correlation identifier groups related activity.

For example:

```text

correlation\_id = TASK-2048

```

may connect:

```text

Observation

Goal

Context

Plan

Decision

ActionRequest

ExecutionResult

Reflection

Experience

```

Correlation is particularly useful for:

* multi-step tasks

* asynchronous processing

* debugging

* telemetry

* replay

* distributed execution

Correlation should not be confused with ownership.

---

# 5.9 Provenance

Important information should retain provenance whenever practical.

Provenance may identify:

* source

* originating subsystem

* timestamp

* transformation

* supporting object

* verification state

Conceptually:

```text

Provenance

├── source

├── source\_type

├── observed\_at

├── produced\_by

├── derived\_from

└── verification

```

Provenance allows RoBoT to distinguish:

> "This was observed."

from:

> "This was inferred."

and:

> "This was remembered from a previous experience."

That distinction is essential to reliable reasoning.

---

# 5.10 Confidence

Contracts that represent uncertain information may carry confidence.

Confidence represents the strength of available evidence.

It does not represent absolute truth.

For example:

```text

confidence = 0.82

```

may indicate that the system currently considers the information well supported.

Confidence may change when new evidence becomes available.

It should therefore be treated as part of the evolving information state rather than a permanent property.

---

# 5.11 Observation

An `Observation` represents information acquired from a source.

Possible sources include:

* user input

* speech recognition

* documents

* files

* sensors

* APIs

* tools

* external systems

* background processes

* other agents

Conceptually:

```text

Observation

├── id

├── timestamp

├── source

├── source\_type

├── content

├── attachments

├── confidence

├── provenance

└── metadata

```

An Observation represents what entered the architecture.

It does not automatically represent what the system believes the information means.

Interpretation occurs downstream.

---

# 5.12 Goal

A `Goal` represents a desired outcome.

A goal may include:

```text

Goal

├── id

├── description

├── priority

├── constraints

├── success\_conditions

├── created\_at

├── deadline

└── status

```

Goals provide direction for planning and reasoning.

A goal is not the same as an action.

For example:

```text

Goal:

"Create a reliable database backup."



Action:

"Run backup command."

```

The goal describes the desired outcome.

The action describes one operation that may contribute to achieving it.

---

# 5.13 Context

A `Context` represents the temporary cognitive environment assembled for a task.

A Context may reference:

* current observations

* active goals

* relevant memories

* relevant experiences

* plans

* skills

* tools

* environmental state

* constraints

Conceptually:

```text

Context

├── id

├── goal\_id

├── observations

├── memory\_references

├── experience\_references

├── active\_plan

├── available\_capabilities

├── constraints

├── created\_at

└── expiration

```

Context is a derived representation.

It is not the authoritative source of the information it contains.

Context should normally be disposable.

---

# 5.14 MemoryRecord

A `MemoryRecord` represents persistent knowledge managed by the Memory Engine.

Examples include:

* facts

* concepts

* entities

* relationships

* summaries

* procedures

* documentation

* learned information

Conceptually:

```text

MemoryRecord

├── id

├── type

├── content

├── summary

├── confidence

├── provenance

├── relationships

├── created\_at

├── updated\_at

├── version

└── status

```

A MemoryRecord may change over time as evidence changes.

Historical versions should remain recoverable when required.

---

# 5.15 ExperienceRecord

An `ExperienceRecord` represents an operational event or sequence of events that produced useful evidence.

Experience may contain:

```text

ExperienceRecord

├── id

├── goal\_id

├── plan\_id

├── decision\_id

├── actions

├── result

├── success

├── execution\_metrics

├── errors

├── lessons

├── confidence\_changes

├── timestamp

└── provenance

```

Experience answers questions such as:

* What happened?

* What was attempted?

* What worked?

* What failed?

* What did the system learn from the attempt?

Experience remains distinct from factual knowledge.

---

# 5.16 Plan

A `Plan` represents a proposed strategy for achieving a goal.

A plan may contain:

```text

Plan

├── id

├── goal\_id

├── steps

├── dependencies

├── required\_skills

├── required\_tools

├── estimated\_cost

├── estimated\_duration

├── estimated\_confidence

├── alternatives

└── status

```

Multiple plans may exist simultaneously.

A plan is a proposal.

It is not proof that the strategy will succeed.

---

# 5.17 Decision

A `Decision` represents a selected course of action resulting from reasoning.

A decision may include:

```text

Decision

├── id

├── goal\_id

├── selected\_plan

├── rationale

├── confidence

├── alternatives\_considered

├── supporting\_evidence

├── assumptions

├── constraints

└── timestamp

```

A decision should remain traceable after execution.

The architecture should be able to determine what information contributed to an important decision.

---

# 5.18 ActionRequest

An `ActionRequest` represents a request to perform an operation.

This is deliberately separate from a Decision.

```text

Decision

   ↓

ActionRequest

   ↓

Authorization

   ↓

Execution

```

An ActionRequest may contain:

```text

ActionRequest

├── id

├── decision\_id

├── action\_type

├── target

├── parameters

├── required\_capabilities

├── authorization\_context

├── constraints

└── timestamp

```

This separation creates an important architectural boundary:

**A decision describes what should happen.**

**An ActionRequest describes what the execution layer has been asked to do.**

---

# 5.19 ExecutionResult

An `ExecutionResult` represents what actually happened during execution.

Possible fields include:

```text

ExecutionResult

├── id

├── action\_request\_id

├── status

├── outputs

├── errors

├── warnings

├── execution\_time

├── resource\_usage

├── observations

├── state\_changes

└── timestamp

```

Execution status should not automatically be interpreted as task success.

For example:

```text

Execution:

SUCCESS



Task:

FAILED

```

The command may have executed correctly while failing to achieve the intended objective.

Reflection determines the broader outcome.

---

# 5.20 Reflection

A `Reflection` represents an evaluation of an outcome.

It may include:

```text

Reflection

├── id

├── goal\_id

├── execution\_id

├── expected\_outcome

├── observed\_outcome

├── success\_assessment

├── errors\_identified

├── assumptions

├── lessons

├── recommendations

└── timestamp

```

Reflection transforms operational results into interpretable evidence.

It is therefore an important bridge between execution and learning.

---

# 5.21 LearningUpdate

A `LearningUpdate` represents a proposed change to persistent cognitive state.

Possible operations include:

```text

LearningUpdate

├── id

├── source\_experience

├── target\_system

├── operation

├── target\_id

├── proposed\_change

├── evidence

├── confidence

├── reason

└── timestamp

```

Examples:

```text

CREATE\_MEMORY

UPDATE\_MEMORY

UPDATE\_CONFIDENCE

ADD\_RELATIONSHIP

REMOVE\_RELATIONSHIP

CREATE\_EXPERIENCE

UPDATE\_SKILL

DEPRECATE\_KNOWLEDGE

```

A LearningUpdate should not directly mutate another subsystem's internal state.

Instead:

```text

Reflection

    ↓

LearningUpdate

    ↓

Owning Subsystem

    ↓

Validation

    ↓

State Change

```

This preserves ownership.

---

# 5.22 Query Contracts

Not all communication creates a new cognitive object.

Subsystems frequently need to request information.

Examples include:

```text

MemoryQuery

ExperienceQuery

ToolQuery

SkillQuery

ObservationQuery

PlanQuery

```

A query should describe what information is needed rather than how the owning subsystem should retrieve it.

Example:

```text

MemoryQuery

├── query

├── filters

├── limit

├── minimum\_confidence

├── time\_range

└── relationship\_constraints

```

The Memory Engine remains responsible for determining how to satisfy the request.

---

# 5.23 Result Contracts

Queries should return structured results.

For example:

```text

MemoryQuery

      ↓

MemoryQueryResult

      ├── records

      ├── relevance

      ├── confidence

      └── metadata

```

The result should provide enough information for the consumer to evaluate the returned data without exposing internal storage implementation.

---

# 5.24 Event Contracts

Events represent things that happened.

Examples include:

```text

ObservationReceived

PlanCreated

DecisionMade

ActionStarted

ActionCompleted

ActionFailed

ReflectionCompleted

MemoryUpdated

ExperienceRecorded

LearningApplied

```

Events are distinct from state.

For example:

```text

Event:

ActionFailed



State:

TaskStatus = Failed

```

An event describes a transition.

State describes a condition.

---

# 5.25 State Contracts

State contracts represent current subsystem or task conditions.

Examples include:

```text

TaskState

ExecutionState

ConversationState

PlannerState

SystemState

MemoryState

```

State should not be confused with history.

If a task is currently marked `FAILED`, that does not replace the historical execution events that explain how it reached that state.

---

# 5.26 Action and Capability Contracts

RoBoT separates the request to perform an action from the capabilities available to perform it.

A capability contract may describe:

```text

Capability

├── id

├── name

├── description

├── inputs

├── outputs

├── permissions

├── cost

├── risk

├── availability

└── version

```

This allows planning and reasoning to consider what RoBoT can actually do.

The capability itself may be implemented by:

* a tool

* a skill

* an MCP server

* a local process

* hardware

* another agent

* an external service

The contract remains independent of the implementation.

---

# 5.27 Ownership

Every persistent cognitive object should have a clearly defined owner.

| Contract | Primary Owner |

| ---------------- | ---------------------------- |

| Observation | Observation System |

| Goal | Planning / Goal Management |

| Context | Context Engine |

| MemoryRecord | Memory Engine |

| ExperienceRecord | Experience Engine |

| Plan | Planning Engine |

| Decision | Reasoning System |

| ActionRequest | Execution / Control Boundary |

| ExecutionResult | Execution Engine |

| Reflection | Reflection System |

| LearningUpdate | Learning Engine |

Ownership means:

> **The owning subsystem controls creation, validation, modification, and persistence of the object.**

Other systems may read or request changes through defined interfaces.

They should not silently modify the owner's internal state.

---

# 5.28 Relationships Between Contracts

Contracts should reference related objects rather than duplicating complete objects whenever practical.

For example:

```text

Goal

  │

  └──► Plan

          │

          └──► Decision

                  │

                  └──► ActionRequest

                           │

                           └──► ExecutionResult

                                    │

                                    └──► Reflection

                                             │

                                             └──► LearningUpdate

```

This keeps objects smaller and preserves clear ownership.

References also allow the architecture to reconstruct the larger history when needed.

---

# 5.29 Immutability and Historical Integrity

Historical records should not silently change.

For example:

```text

Decision D-100

confidence = 0.72

```

If later evidence changes confidence, the architecture should preserve the historical decision.

A later record may indicate:

```text

Decision Evaluation

previous\_confidence = 0.72

new\_confidence = 0.41

reason = contradictory evidence

```

This preserves the distinction between:

**What RoBoT believed then**

and:

**What RoBoT believes now.**

That distinction is valuable for learning and debugging.

---

# 5.30 Schema Versioning

Every persisted or externally exchanged contract should be versionable.

Conceptually:

```text

schema\_version = 1

```

When a contract evolves:

```text

v1

 ↓

v2

 ↓

v3

```

The architecture should support migration or compatibility strategies appropriate to the object.

Versioning applies to:

* stored records

* serialized messages

* APIs

* events

* persisted experiences

* historical data

Internal implementation versions do not necessarily need to match contract versions.

---

# 5.31 Backward Compatibility

When practical, newer systems should remain capable of consuming older contract versions.

For example:

```text

Old Producer

    ↓

Contract v1

    ↓

Compatibility Layer

    ↓

New Consumer

```

Compatibility is especially important for persistent memories and experiences because historical data may remain valuable long after the software that created it has been replaced.

---

# 5.32 Validation

Incoming contracts should be validated before they are trusted.

Validation may include:

* required fields

* type validation

* identifier validation

* schema version

* ownership

* authorization

* value ranges

* relationship integrity

* provenance

* security classification

Conceptually:

```text

Incoming Contract

       ↓

Schema Validation

       ↓

Semantic Validation

       ↓

Authorization

       ↓

Accept / Reject

```

Schema validity does not guarantee semantic correctness.

A contract can be structurally valid while containing incorrect information.

---

# 5.33 Serialization

Contracts should be serializable without depending on a particular storage engine.

Potential representations may include:

* JSON

* binary formats

* database records

* message envelopes

* Rust structures

* API payloads

The serialized representation is an implementation detail.

The conceptual contract remains authoritative.

---

# 5.34 Replayability

Contracts should support replay where practical.

A historical sequence may be reconstructed:

```text

Observation

   ↓

Goal

   ↓

Plan

   ↓

Decision

   ↓

ActionRequest

   ↓

ExecutionResult

   ↓

Reflection

   ↓

LearningUpdate

```

Replayability enables:

* debugging

* regression testing

* failure analysis

* system evaluation

* simulation

* architecture research

Replay does not necessarily mean executing real-world actions again.

The architecture should distinguish between replaying cognitive history and re-performing external actions.

---

# 5.35 Testing

Data contracts provide stable testing boundaries.

Each subsystem can be tested using known contract inputs.

For example:

```text

Test Input

    ↓

Observation

    ↓

Context Engine

    ↓

Expected Context

```

Likewise:

```text

Test ExecutionResult

        ↓

Reflection

        ↓

Expected Reflection

```

This allows subsystems to be tested independently without requiring the entire RoBoT architecture to run.

---

# 5.36 Error Contracts

Errors should also follow structured contracts.

A conceptual error object may contain:

```text

Error

├── id

├── code

├── category

├── message

├── subsystem

├── operation

├── severity

├── recoverable

├── correlation\_id

├── cause

└── timestamp

```

Structured errors allow the architecture to distinguish between:

* transient failures

* invalid input

* permission failures

* unavailable resources

* tool failures

* logic failures

* infrastructure failures

* unrecoverable conditions

Errors are information and should be capable of entering the normal observation and experience flows.

---

# 5.37 Contract Boundaries

A subsystem should expose contracts at its boundary rather than its internal data structures.

For example:

```text

                MEMORY ENGINE

        ┌──────────────────────────┐

        │                          │

        │   Internal Storage       │

        │   Graph Structures       │

        │   Embeddings             │

        │   Indexes                │

        │                          │

        └────────────┬─────────────┘

                     │

              Contract Boundary

                     │

                     ▼

              MemoryQuery

              MemoryResult

              MemoryUpdate

```

The internal implementation may change completely while the contract remains stable.

This is one of the primary mechanisms that allows RoBoT to evolve.

# 5.39 Contract Evolution

New contracts should be introduced only when existing contracts cannot adequately represent a distinct concept.

Before creating a new object, determine whether the requirement is actually:

* a new field

* a new relationship

* a new event

* a new query

* a new state

* a new action

* a new contract

Avoid creating new objects simply because a subsystem wants a convenient internal representation.

The contract layer should remain understandable as the architecture grows.

# 5.41 Core Contract Invariants

The following rules should remain stable unless the architecture is deliberately revised.

### Invariant 1

**Contracts describe meaning, not implementation.**

### Invariant 2

**Every important contract has a defined owner.**

### Invariant 3

**Published historical objects should be immutable by default.**

### Invariant 4

**Contract schemas are versioned.**

### Invariant 5

**Important objects retain identity and provenance whenever practical.**

### Invariant 6

**Consumers do not directly modify another subsystem's owned state.**

### Invariant 7

**A structurally valid contract is not automatically truthful.**

### Invariant 8

**Events describe what happened; state describes current condition.**

### Invariant 9

**Decisions, actions, and execution results remain distinct concepts.**

### Invariant 10

**Learning updates are proposals or controlled state transitions, not unrestricted database mutations.**

### Invariant 11

**Contracts should remain small enough to understand and stable enough to evolve.**

### Invariant 12

**Historical information should remain distinguishable from current interpretation.**

## Final v0.0.2.1 Integration Contract

This chapter is normative within the v0.0.2.1 architecture. Its subject matter must integrate with the architecture-wide contract in `FINAL_ARCHITECTURE_SPEC.md`.

### Required cross-boundary behavior

1. **Ownership:** This chapter defines or refines responsibilities without taking ownership of another subsystem's durable state.
2. **Lifecycle:** Every state or operation introduced here has explicit creation, active, completion, failure, retention, expiration, or archival behavior as applicable.
3. **Identity:** Operations retain the correlation and entity identifiers needed to reconstruct their relationship to conversations, goals, plans, actions, executions, experiences, events, and configuration changes.
4. **Evidence:** Observed information, inferred information, candidate changes, evaluated information, and promoted knowledge remain distinguishable.
5. **Uncertainty:** Missing information, contradiction, confidence, and unresolved conditions are represented rather than silently collapsed.
6. **Failure:** Errors, retries, partial completion, cancellation, recovery, and terminal failure remain observable.
7. **Model independence:** This chapter must not require persistent state to live inside a particular model, prompt format, inference runtime, or context window.
8. **Controlled effects:** Any external or privileged effect must pass through the appropriate authorization, execution, validation, and audit boundary.
9. **Observability:** Important state transitions and outcomes must produce structured evidence suitable for monitoring and reconstruction.
10. **Versioning:** Changes to contracts, schemas, events, or lifecycle semantics require explicit versioning and compatibility handling.
11. **GUI/control-plane integration:** When this chapter exposes functionality to humans, the GUI communicates through the Developer Interface and Control Plane. It must not directly mutate subsystem storage or bypass security.
12. **Testing:** The chapter's architectural guarantees must be testable through the testing architecture defined in Chapter 30.
