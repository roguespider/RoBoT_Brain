# Chapter 11. Planning Engine

**Architecture Version:** v0.0.2.1  
**Document Role:** Normative architectural chapter  
**v0.0.2.1 Focus:** Goal/task/plan separation, plan validation, dependencies, contingencies, confidence and replanning  




## Purpose



The Planning Engine transforms objectives into structured, adaptive strategies that can be executed by RoBoT.



While the Conversation Engine determines **what the user wants**, the Context Engine determines **what is currently relevant**, the Memory Engine provides **what RoBoT knows**, the Experience Engine provides **what RoBoT has previously done**, and the Learning Engine provides **what RoBoT has learned**, the Planning Engine determines:



> **What should happen next, in what order, under which constraints, and why?**



The Planning Engine is therefore the bridge between cognition and execution.



It does not perform work itself.



It does not directly execute tools.



It does not replace reasoning.



Instead, it converts objectives, evidence, constraints, capabilities, and learned strategies into an explicit plan that can be validated, executed, monitored, and revised.



The planner must assume that the world can change after planning begins.



Therefore, planning is not a one-time operation.



It is a continuous control loop:



```text

Goal

  │

  ▼

Understand

  │

  ▼

Plan

  │

  ▼

Validate

  │

  ▼

Execute

  │

  ▼

Observe

  │

  ▼

Compare

  │

  ▼

Replan

  │

  └───────────────►

```



The Planning Engine exists to ensure that RoBoT does not merely produce actions.



It produces **purposeful actions connected to objectives, dependencies, evidence, constraints, and measurable outcomes.**



---



# 11.1 Philosophy



Planning is not prompting.



Planning is structured decision-making over time.



An LLM can generate a plausible sequence of actions, but plausibility is not sufficient for reliable autonomous operation.



A planning system must understand:



* what the objective actually is

* what constitutes success

* what information is missing

* what assumptions are being made

* what constraints exist

* what resources are available

* what dependencies exist

* what risks are present

* what alternatives are available

* what has already been attempted

* what previously worked

* what previously failed

* what should happen next

* whether the current plan is still valid



The planner therefore treats every plan as a **hypothesis about how an objective can be achieved**.



Execution provides evidence about whether that hypothesis was correct.



The planner then updates the plan based on that evidence.



This creates a continuous cycle:



```text

Plan

  ↓

Act

  ↓

Observe

  ↓

Evaluate

  ↓

Learn

  ↓

Replan

```



A plan is therefore not a rigid script.



It is a controlled, inspectable strategy that can evolve as conditions change.

* Goal analysis

* Strategy selection

* Execution coordination

* Progress tracking

* Execution monitoring

* Dynamic replanning

* Failure recovery planning

Learning and heuristic evolution belong to the Learning Engine.

# 11.4 Core Planning Concepts



RoBoT distinguishes between several concepts that must not be collapsed into a single structure.



## Goal



A desired outcome.



```text

Goal = What should ultimately be achieved?

```



Example:



```text

Implement graph memory.

```



## Plan



A strategy for achieving the goal.



```text

Plan = How do we intend to achieve it?

```



## Task



A discrete unit of work within the plan.



```text

Task = What specific work must be performed?

```



## Action



An executable operation associated with a task.



```text

Action = What operation should actually occur?

```



## Observation



Evidence produced by execution or the external environment.



```text

Observation = What actually happened?

```



## Result



The evaluated outcome of an action or task.



```text

Result = What did the action accomplish?

```



## Decision



A planner conclusion based on available evidence.



```text

Decision = What should happen next?

```



These distinctions prevent the planner from becoming a single opaque structure containing goals, actions, execution state, and historical results.

# 11.5 Goal Management



The Goal Manager maintains every active objective known to the planning system.



A goal contains:



```text

Goal

{

    id

    description

    objective

    priority

    status

    parent\_goal

    child\_goals

    success\_criteria

    constraints

    assumptions

    deadline

    confidence

    created\_at

    updated\_at

}

```



Goals may exist for:



* seconds

* minutes

* hours

* days

* months

* indefinitely



The lifetime of a goal must not depend on the lifetime of a conversation.



A conversation may end while its underlying objective remains active.



This allows RoBoT to support long-running objectives such as:



```text

Build Memory System

    │

    ├── Design Database

    ├── Implement Retrieval

    ├── Implement Graph Memory

    ├── Implement Compression

    ├── Benchmark

    └── Document

```



---



# 11.6 Goal Hierarchy



Large objectives are recursively decomposed into smaller objectives.



```text

Build RoBoT

│

├── Build Memory

│   ├── Database

│   ├── Retrieval

│   ├── Graph

│   └── Compression

│

├── Build Experience

│

├── Build Learning

│

├── Build Planning

│

└── Build Testing

```



A child goal inherits relevant constraints and context from its parent while maintaining its own success criteria.



This produces a hierarchical objective structure rather than an unstructured task list.



---



# 11.7 Goal Completion



A goal is not considered complete merely because its tasks finished.



Completion requires verification against its success criteria.



```text

Tasks Complete

      │

      ▼

Results Available

      │

      ▼

Success Criteria Evaluated

      │

      ▼

Goal Verified

      │

      ▼

Goal Completed

```



This distinction is critical.



Execution completion and objective completion are not necessarily the same thing.



---



# 11.8 Goal Decomposition



Large objectives are recursively broken into independently manageable units.



Example:



```text

Goal:

Implement Memory Search



        │

        ▼



Analyze Existing Architecture



        │

        ▼



Locate Database Layer



        │

        ▼



Locate Retrieval Layer



        │

        ▼



Design Search Interface



        │

        ▼



Implement Search



        │

        ▼



Run Tests



        │

        ▼



Measure Performance



        │

        ▼



Verify Results



        │

        ▼



Update Documentation

```



The planner should continue decomposing a task until it becomes sufficiently concrete for execution.



However, decomposition should not continue indefinitely.



Over-decomposition creates planning overhead and unnecessary complexity.



The planner therefore determines an appropriate planning granularity based on:



* task complexity

* uncertainty

* risk

* execution cost

* available capabilities

* dependency structure

# 11.9 Task Graph



Tasks are represented as a dependency graph.



Whenever dependencies permit, the graph should remain a Directed Acyclic Graph (DAG).



```text

        A

      /   \\

     B     C

      \\   /

        D

        │

        ▼

        E

```



For example:



```text

A = Design schema

B = Implement database

C = Implement retrieval

D = Integrate systems

E = Run tests

```



B and C may execute independently.



D cannot begin until both B and C are complete.



This representation enables:



* parallel execution

* dependency awareness

* prioritization

* checkpointing

* partial completion

* failure isolation

* targeted replanning



Cyclic dependencies must be detected before execution.

Dependencies may exist between:



* tasks

* goals

* files

* databases

* APIs

* tools

* permissions

* resources

* knowledge

* external systems

* prerequisite decisions



A task may therefore be blocked even when its previous task is complete.



Example:



```text

Implement Feature

      │

      ▼

Requires Database Schema

      │

      ▼

Requires Architecture Decision

      │

      ▼

Requires User Clarification

```



The planner must understand these dependency chains before execution begins.

# 11.11 Constraints



Every plan operates under constraints.



Examples include:



* time

* CPU

* GPU

* memory

* storage

* API limits

* rate limits

* token budgets

* financial cost

* permissions

* security policies

* user requirements

* architecture rules

* operating agreements

* environmental limitations



Constraints may be:



### Hard Constraints



The plan cannot violate them.



Example:



```text

Do not modify protected files.

```



### Soft Constraints



The planner may violate them if the expected benefit justifies doing so.



Example:



```text

Prefer lower-cost execution.

```



The Constraint Manager continuously validates the plan against both categories.

# 11.12 Assumptions



Plans are frequently based on incomplete information.



The planner therefore records assumptions explicitly.



```text

Assumption

{

    id

    description

    source

    confidence

    criticality

    status

}

```



Example:



```text

Assumption:

The database schema supports graph relationships.



Confidence:

0.72

```



If an important assumption becomes invalid, the planner may need to replan.



This prevents hidden assumptions from silently controlling long-running behavior.



---



# 11.13 Evidence



Planning decisions should be grounded in available evidence whenever possible.



Evidence may originate from:



* current context

* memory

* previous experience

* tool results

* observations

* learned heuristics

* user instructions

* world state



A planning decision should therefore be traceable to the information that influenced it.



This is particularly important for debugging autonomous behavior.



---



# 11.14 Priority Management



Every active task receives a dynamic priority.



Priority may consider:



* urgency

* importance

* dependency depth

* expected benefit

* deadline proximity

* user preference

* historical success

* execution cost

* confidence

* risk

* downstream impact



Priority is not static.



A task that was low priority five minutes ago may become critical after another task fails.



---



# 11.15 Strategy Selection



Many objectives have multiple valid strategies.



Example:



```text

Need Information

       │

       ▼

Check Memory

       │

       ├── Found ─────► Use Memory

       │

       └── Not Found

              │

              ▼

        Check Local Data

              │

              ├── Found ─► Use Local Data

              │

              └── Not Found

                     │

                     ▼

                  Web Search

                     │

                     └── If insufficient

                              │

                              ▼

                          Ask User

```



The planner evaluates candidate strategies rather than blindly selecting the first available mechanism.



Strategy selection may consider:



* expected success

* reliability

* latency

* cost

* risk

* available evidence

* historical performance

* tool availability

* confidence



The preferred strategy is the one with the highest expected value under current conditions.

# 11.16 Tool Planning



The Planning Engine determines **what capability is required**.



The Tool System determines **how that capability is actually provided**.



The planner may specify:



```text

Requirement:

Read repository file



Required capability:

filesystem.read



Constraints:

read-only

```



The Tool System can then resolve that requirement to an appropriate implementation.



This separation prevents the Planning Engine from becoming tightly coupled to individual MCP tools.



Tool evaluation may consider:



* capability

* reliability

* availability

* historical success

* latency

* cost

* security

* permissions

* expected output quality



The planner should prefer capabilities rather than hard-coded tool identities whenever practical.

# 11.17 Agent Planning

* Research Agent

* Coding Agent

The Planning Engine may determine:



* which agent is appropriate

* conflict resolution

* verification requirements



The current architecture remains fully functional in single-agent mode.



Multi-agent orchestration is an extension of the planning model rather than a replacement for it.

# 11.21 Plan Versioning



Plans are mutable.



Whenever significant planning decisions change, the planner creates a new plan version.



```text

Plan v1

  │

  ├── Task A

  ├── Task B

  └── Task C

       │

       ▼

Observation

       │

       ▼

Plan v2

  │

  ├── Task A

  ├── Task B

  └── Task D

```



Previous versions should remain traceable.



Plan versioning provides:



* debugging

* reproducibility

* decision history

* failure analysis

* auditability

* comparison of strategies



The planner should modify only the affected portion of a plan whenever practical.

```text

      │

      ▼

Execution Engine

      │

      │ performs

      ▼

Actions

      │

      ▼

      │

      ▼
```

The planner specifies:



* what should happen

* prerequisites

* ordering

* priority

* required capabilities

* constraints

* how actions are dispatched

* how tools are invoked

* how processes run

* how execution errors are surfaced

# 11.24 Dynamic Replanning



Replanning occurs when the current plan is no longer the best known strategy.



Triggers include:



* new user instructions

* tool failure

* missing information

* changed world state

* invalid assumptions

* memory updates

* experience updates

* learning updates

* unexpected outputs

* changed priorities

* newly discovered dependencies

* resource constraints



Replanning should be **incremental whenever possible**.



The planner should not rebuild an entire long-running plan merely because one task changed.



Instead:



```text

Existing Plan

     │

     ▼

Identify Affected Tasks

     │

     ▼

Preserve Valid Work

     │

     ▼

Replace Invalid Branch

     │

     ▼

Validate New Plan

     │

     ▼

Continue

```



This minimizes wasted computation and preserves useful progress.

# 11.25 Checkpoints



Long-running plans create checkpoints.



A checkpoint records sufficient information to resume planning and execution safely.



```text

Checkpoint

{

    plan\_version

    completed\_tasks

    active\_tasks

    pending\_tasks

    outputs

    assumptions

    confidence

    resource\_usage

    world\_state

    remaining\_work

    created\_at

}

```



Checkpoints provide recovery after:



* process termination

* system restart

* tool failure

* context loss

* execution interruption

* infrastructure failure



A long-running objective should therefore not depend on one uninterrupted execution session.


The appropriate recovery depends on:

* retry history

* confidence

* cost

* risk

* available alternatives

* importance of the task



Every meaningful recovery attempt becomes execution experience that can later improve planning.

# 11.28 Planning State



The Planning Engine maintains a persistent planning state.



```text

{

    active\_goals

    active\_tasks

    task\_graph

    plan\_version

    constraints

    assumptions

    evidence

    risks

    priorities

    strategies

    required\_capabilities

    selected\_tools
```

Planning state is distinct from Context.

Planning State represents the current state of an objective and its strategy.



This distinction allows plans to survive context reconstruction and conversation boundaries.

# 11.33 Explainability and Traceability



Every significant planning decision should be traceable.



The planner should be able to answer:



```text

Why was this task created?



Why was this dependency required?



Why was this strategy selected?



Why was this tool capability required?



Why was this task prioritized?



Why was replanning triggered?



Which evidence influenced the decision?



Which assumptions were involved?

What changed between plan versions?

```



This does not require exposing private chain-of-thought.



It requires maintaining structured decision metadata sufficient for engineering, debugging, auditing, and system improvement.

# 11.34 Design Principles



The Planning Engine follows these principles:



### 1. Plans Are Explicit



Plans are structured, inspectable, versioned objects rather than hidden prompt instructions.



### 2. Goals Are Persistent



Long-running objectives may survive conversations and execution sessions.



### 3. Planning Is Iterative



A plan is continuously evaluated against reality.



### 4. Execution Is Separate



The planner decides what should happen.



The Execution Engine performs it.



### 5. Evidence Drives Decisions



Planning should use Context, Memory, Experience, Learning, and current observations.



### 6. Dependencies Are Explicit



Tasks should not rely on invisible ordering assumptions.



### 7. Assumptions Are Tracked



Important assumptions must be visible and revisable.



### 8. Failure Is Recoverable



Failure should trigger evaluation and recovery rather than automatically terminating an objective.



### 9. Replanning Is Normal



Changing the plan is an expected behavior, not an exceptional failure.



### 10. Progress Is Measurable



Tasks and goals require observable completion criteria.



### 11. Plans Are Incrementally Modified



Valid work should be preserved whenever possible.



### 12. Planning Decisions Are Traceable



Important decisions must be explainable through structured evidence and metadata.



### 13. Learning Improves Planning



Execution outcomes must feed Experience and Learning so future planning becomes more effective.

# 11.36 Integration Summary



The Planning Engine is the executive coordination layer of RoBoT.



It transforms objectives into explicit strategies by combining current context, persistent knowledge, historical experience, learned heuristics, available capabilities, constraints, and environmental state.



Unlike a static task generator, the Planning Engine operates continuously throughout execution.



It creates goals, defines success criteria, decomposes objectives, constructs dependency graphs, evaluates strategies, estimates cost and risk, validates plans, coordinates execution, monitors progress, and dynamically replans when conditions change.



The planner does not directly perform work.



Instead, it maintains the strategic state required for the Execution Engine to perform purposeful work safely and coherently.



Its most important architectural property is therefore not the ability to generate plans.



It is the ability to **maintain and revise plans over time**.



Through checkpoints, persistent goals, explicit assumptions, plan versioning, structured dependencies, measurable success criteria, and continuous observation, RoBoT can pursue objectives that extend beyond a single reasoning cycle or conversation.



Most importantly, every completed objective creates an opportunity for improvement.



The Experience Engine records what happened.



The Learning Engine determines what should be learned from it.



The Planning Engine incorporates those lessons into future strategies.



This establishes the foundation for increasingly capable autonomous behavior:



```text

Goal

  ↓

Plan

  ↓

Execute

  ↓

Observe

  ↓

Experience

  ↓

Learning

  ↓

Improved Planning

  ↓

Better Execution

  ↓

More Capable RoBoT

```



The Planning Engine therefore serves as the **strategic control system of RoBoT**, transforming intention into coordinated action while continuously adapting to reality.
