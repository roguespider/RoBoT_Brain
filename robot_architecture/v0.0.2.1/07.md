# Chapter 07 — Context Engine

**Architecture Version:** v0.0.2.1  
**Document Role:** Normative architectural chapter  
**v0.0.2.1 Focus:** Bounded temporary context, deterministic assembly, relevance, provenance, expiration, reconstructability  


**Status:** Architectural Specification

---

## 7.1 Purpose

The Context Engine is RoBoT's **cognitive context assembly system**.

Its purpose is to determine what information should be available to the current reasoning cycle and construct a temporary, structured context from that information.

Memory stores information.

Knowledge provides authoritative information.

Experience records what happened and what was learned from outcomes.

Planning determines what must be accomplished.

The Context Engine brings the relevant portions of these systems together for the current cognitive operation.

Its fundamental question is:

> **What information matters right now?**

The Context Engine transforms potentially enormous amounts of available information into a bounded working context suitable for reasoning.

```text

Persistent Information

        │

        ├── Memory

        ├── Knowledge

        ├── Experience

        ├── Goals

        └── Skills

        │

        ▼

Context Requirements

        │

        ▼

Context Selection

        │

        ▼

Context Ranking

        │

        ▼

Context Compression

        │

        ▼

Token Budget

        │

        ▼

Active Cognitive Context

        │

        ▼

Reasoning

```

Without this separation, an AI system eventually encounters one of two failures:

* too little information to make a useful decision

* too much information to reason efficiently

The Context Engine exists to maintain the boundary between those extremes.

---

# 7.2 Architectural Philosophy

RoBoT does not attempt to place its entire lifetime of information into every reasoning operation.

The architecture assumes that most available information is irrelevant to any individual cognitive operation.

A reasoning cycle therefore begins with an intentionally limited working environment.

```text

Available Information

        │

        ▼

Relevance Determination

        │

        ▼

Selected Information

        │

        ▼

Active Context

        │

        ▼

Reasoning

```

When the reasoning cycle completes, the assembled context is no longer automatically retained.

Temporary information disappears unless another subsystem determines that it has persistent value.

This establishes a critical separation:

> **Availability does not imply inclusion.**

Information may exist within RoBoT without being loaded into the current context.

---

# 7.3 Context Is Not Memory

Context and memory are related but fundamentally different concepts.

| Memory | Context |

| ---------------------- | ------------------ |

| Persistent | Temporary |

| Potentially very large | Explicitly bounded |

| Stored | Assembled |

| Indexed | Selected |

| Historical | Current |

| Reusable | Task-specific |

| Retrieval source | Retrieval result |

| Long-lived | Short-lived |

Memory answers:

> **What does RoBoT know or remember?**

Context answers:

> **What does RoBoT need available for this operation?**

The Context Engine therefore does not replace the Memory Engine.

It consumes information from memory and other systems to construct the current cognitive state.

# 7.5 Responsibilities

The Context Engine is responsible for:

* receiving context requirements

* determining required context categories

* requesting relevant information

* combining context sources

* ranking candidate information

* resolving duplication

* maintaining temporary working context

* tracking active conversational references

* managing context layers

* compressing information

* enforcing context budgets

* prioritizing information

* exposing context composition for observability

* discarding temporary context when its lifetime ends

The Context Engine does **not** own:

* permanent memory

* knowledge

* experience

* planning

* reasoning

* tool implementations

* model inference

* permanent user information

Its role is assembly and management.

---

# 7.6 Context Requirements

The Context Engine should not blindly retrieve information.

Instead, it receives or derives a set of **context requirements** describing what the current cognitive operation needs.

Conceptually:

```text

ContextRequirements



Intent

Goals

Task

Entities

Topic

Required Knowledge

Required Memory

Required Experience

Required Skills

Required Tools

Planner Requirements

Output Requirements

Constraints

Priority

Token Budget

```

The requirements determine what categories of information should be considered.

For example, a simple factual question may require:

```text

Knowledge

Conversation Continuity

Relevant User Context

```

A complex debugging operation may require:

```text

Conversation History

Code

Architecture

Previous Failures

Relevant Documentation

Active Task

Tool State

Planner State

```

The Context Engine adapts to the operation rather than constructing the same context for every request.

# 7.7 Context Layers

The active context may contain multiple independent layers.

```text

Active Context

│

├── System Constraints

├── Conversation Context

├── Working Memory

├── Active Goals

├── Task State

├── Retrieved Memories

├── Relevant Experiences

├── Knowledge References

├── Active Skills

├── Current Environment

├── Recent Observations

├── Planner State

├── Tool State

└── Execution Results

```

Each layer has an independent semantic purpose.

This allows the Context Engine to modify or remove one category without rebuilding unrelated context.

---

# 7.8 Context Ownership

Information ownership remains with the originating subsystem.

| Information | Owner | Context Engine |

| ------------------ | ---------------------- | -------------- |

| Permanent memories | Memory Engine | Selects |

| Knowledge | Knowledge System | Selects |

| Experiences | Experience Engine | Selects |

| Goals | Goal / Planning System | Loads |

| Plans | Planning Engine | Loads |

| Skills | Skill System | Selects |

| Tool results | Execution System | Includes |

| Conversation state | Conversation Engine | Includes |

| Working context | Context Engine | Owns |

| Model context | LLM Interface | Consumes |

This prevents the Context Engine from becoming an accidental secondary database.

# 7.9 Context Lifecycle

Every cognitive operation follows a context lifecycle.

```text

Context Requirements

        │

        ▼

Identify Required Sources

        │

        ▼

Retrieve Candidates

        │

        ▼

Normalize Candidates

        │

        ▼

Rank Candidates

        │

        ▼

Resolve Conflicts

        │

        ▼

Deduplicate

        │

        ▼

Compress

        │

        ▼

Allocate Token Budget

        │

        ▼

Construct Active Context

        │

        ▼

Validate Context

        │

        ▼

Reasoning

        │

        ▼

Context Finalization

        │

        ▼

Discard Temporary Context

```

The lifecycle may repeat when new information arrives.

For example:

```text

Plan

 ↓

Retrieve Context

 ↓

Execute Tool

 ↓

Tool Result

 ↓

Update Context

 ↓

Reason

 ↓

Execute Another Tool

 ↓

Update Context

```

Context is therefore not necessarily assembled only once per user message.

# 7.10 Conversation Context

Conversation context preserves the information required to maintain continuity.

It may contain:

* recent dialogue

* unresolved questions

* current topic

* active assumptions

* user corrections

* decisions

* references

* pronoun relationships

* current goals

* relevant prior exchanges

The Context Engine should not replay the entire conversation merely because it exists.

Instead, older information is progressively summarized or retrieved when relevant.

```text

Recent Conversation

        │

        ├── High relevance → retain directly

        │

        ├── Moderate relevance → summarize

        │

        └── Low relevance → retrieve only if needed

```

This keeps conversational continuity without allowing history to consume the entire reasoning window.

---

# 7.11 Working Context

Working context is temporary information required during the current cognitive operation.

Examples include:

* intermediate facts

* temporary variables

* unresolved references

* active calculations

* temporary assumptions

* tool results

* partial task state

* intermediate planning information

```text

Working Context

      │

      ├── Temporary Facts

      ├── Intermediate Results

      ├── Active References

      ├── Tool Results

      └── Current Reasoning State

```

Working context is disposable.

It must not automatically become long-term memory.

---

# 7.12 Memory Integration

The Context Engine requests relevant information from the Memory Engine.

Memory retrieval may provide:

* semantic memories

* episodic memories

* procedural knowledge

* indexed facts

* relationship information

* historical summaries

Candidate memories should contain sufficient metadata to support selection.

Conceptually:

```text

MemoryCandidate



MemoryID

Content

Relevance

Confidence

Importance

Freshness

Source

Relationships

Timestamp

```

The Context Engine uses this information to determine whether the memory belongs in the current context.

The Memory Engine remains responsible for storage, indexing, retrieval mechanisms, and persistence policy.

---

# 7.13 Experience Integration

Experience provides information about previous outcomes.

Examples include:

* successful workflows

* failed approaches

* tool failures

* effective strategies

* unsuccessful strategies

* confidence changes

* historical execution results

Experience can influence context selection.

For example:

```text

Current Task

     │

     ▼

Experience Retrieval

     │

     ├── Previous Successful Approach

     ├── Previous Failure

     └── Known Constraint

     │

     ▼

Relevant Experience

```

This allows previous outcomes to influence current behavior without treating experience as ordinary factual memory.

---

# 7.14 Knowledge Integration

Knowledge systems provide information considered authoritative or useful for the current task.

Examples include:

* documentation

* source code

* technical references

* indexed files

* APIs

* manuals

* structured facts

* schemas

The Context Engine selects relevant knowledge according to the requirements of the current operation.

Knowledge remains owned by its source system.

---

# 7.15 Context Ranking

Candidate information must be ranked before inclusion.

A conceptual scoring model is:

```text

Context Score =

    Relevance

  × Confidence

  × Recency

  × Importance

  × Goal Match

  × Conversation Match

  × Planner Priority

  × Source Quality

```

This is a conceptual architecture rather than a mandatory mathematical implementation.

Different retrieval systems may use different scoring strategies.

The architectural requirement is that context selection should consider **multiple signals** rather than relying exclusively on vector similarity.

---

# 7.16 Relevance

Relevance determines how strongly a candidate relates to the current operation.

Possible signals include:

* semantic similarity

* entity overlap

* topic relationship

* task relationship

* goal relationship

* temporal relevance

* explicit user references

* planner requirements

Relevance should be evaluated relative to the **current cognitive operation**, not merely the current conversation.

---

# 7.17 Confidence

Confidence represents how strongly RoBoT should trust a candidate item.

Confidence may originate from:

* source reliability

* repeated confirmation

* historical accuracy

* user confirmation

* system validation

* experience

* knowledge provenance

Confidence should not be confused with relevance.

An item can be:

```text

Highly Relevant + Low Confidence

```

or:

```text

Highly Confident + Irrelevant

```

Both dimensions matter independently.

---

# 7.18 Recency

Recent information is often more relevant, but recency must not automatically override older information.

For example:

```text

Recent Temporary Fact

```

may be more useful than:

```text

Old General Knowledge

```

for one task.

However:

```text

Recent Error

```

should not automatically override:

```text

Long-established Verified Knowledge

```

The Context Engine therefore treats recency as one ranking factor rather than a universal priority rule.

---

# 7.19 Importance

Some information deserves retention even when it is not immediately dominant.

Examples include:

* critical constraints

* user corrections

* task requirements

* safety restrictions

* important decisions

* architectural invariants

* unresolved blockers

Importance allows such information to survive aggressive context reduction.

---

# 7.20 Deduplication

Multiple systems may return information representing the same underlying fact.

For example:

```text

Memory A → "RoBoT uses SQLite."

Knowledge B → "Database implementation uses SQLite."

Experience C → "SQLite migration was completed."

```

These are related but not necessarily identical.

The Context Engine should:

1\. identify duplicates

2\. merge equivalent information

3\. preserve distinct information

4\. preserve provenance

5\. preserve relationships

Deduplication must not destroy useful distinctions.

---

# 7.21 Conflict Resolution

Context sources may disagree.

For example:

```text

Memory → Version 1

Documentation → Version 2

Recent Tool Result → Version 3

```

The Context Engine should not silently select one without considering provenance and authority.

A conceptual resolution process is:

```text

Conflicting Information

        │

        ▼

Source Evaluation

        │

        ├── Authority

        ├── Confidence

        ├── Freshness

        ├── Verification

        └── Context Relevance

        │

        ▼

Resolved Context

```

When uncertainty remains significant, the conflict itself may need to remain visible to the reasoning system.

---

# 7.22 Context Compression

Large amounts of information must sometimes be compressed.

Compression should preserve the information necessary for future reasoning.

Important properties include:

* facts

* relationships

* decisions

* constraints

* provenance

* confidence

* unresolved questions

* references

Compression must not invent information.

Conceptually:

```text

Raw Information

       │

       ▼

Relevant Information

       │

       ▼

Structured Summary

       │

       ▼

Compressed Context

```

Compression is therefore information reduction, not information fabrication.

---

# 7.23 Progressive Conversation Compression

Long conversations require progressive summarization.

```text

Recent Messages

      │

      ▼

Conversation Summary

      │

      ▼

Compressed History

      │

      ▼

Persistent Memory / Checkpoint

```

However, compression must remain reversible through retrieval whenever possible.

A summary should contain references that allow the underlying information to be located again.

This produces a hierarchy:

```text

Detailed History

      │

      ▼

Conversation Checkpoint

      │

      ▼

Compressed Summary

      │

      ▼

Long-Term Memory

```

The appropriate persistence level is determined by the Memory and Learning systems rather than by compression alone.

---

# 7.24 Topic Tracking

The Context Engine tracks the current conversational and task topic.

Possible topics include:

```text

Architecture

Programming

Debugging

Planning

Research

Learning

General Conversation

```

Topic tracking helps determine which information remains relevant.

A topic transition does not erase previous work.

Instead:

```text

Topic A

  │

  ▼

Compressed / Stored Context

  │

  ▼

Topic B

  │

  ▼

New Active Context

```

When the user returns to Topic A, relevant information can be retrieved again.

---

# 7.25 Entity Tracking

The Context Engine maintains active entity references.

For example:

```text

RoBoT

Rust

SQLite

Memory Engine

Context Engine

Planning Engine

GitHub Repository

```

Entities may connect to:

* memories

* documents

* relationships

* goals

* tasks

* experiences

* conversation references

Entity tracking helps resolve statements such as:

> "Update that one."

The system can use the active entity graph and recent context to determine what "that one" refers to.

Entity resolution remains contextual and should not be treated as permanent knowledge by default.

RoBoT does not treat the model context window as one undifferentiated block.

Instead, the active context may be layered:

```text

┌──────────────────────────────┐

│ System Constraints           │

│ Current Interaction          │

├──────────────────────────────┤

│ Conversation Continuity      │

├──────────────────────────────┤

│ Active Goals / Task State    │

├──────────────────────────────┤

│ Planner State                │

├──────────────────────────────┤

│ Relevant Memory              │

├──────────────────────────────┤

│ Relevant Experience          │

├──────────────────────────────┤

├──────────────────────────────┤

│ Tools / Execution Results    │

```

The exact representation may vary by model and runtime.

The architectural principle remains:

> **Context should be structured before it becomes model input.**

# 7.27 Token Budget Management

The Context Engine enforces an explicit budget.

A conceptual allocation might be:

| Context Layer | Example Allocation |

| -------------------- | -----------------: |

| System / Constraints | 5% |

| Current Interaction | 10% |

| Conversation | 20% |

| Memory | 20% |

| Experience | 15% |

| Knowledge | 15% |

| Planner / Task | 10% |

| Tools / Execution | 5% |

These percentages are examples, not fixed architectural requirements.

Budgets should adapt to task type.

For example:

```text

Coding Task

→ More Knowledge / Tool Context



Planning Task

→ More Goal / Planner Context



Conversation

→ More Conversation Context



Research

→ More Knowledge Context

```

The budget system should protect critical information from being displaced by less important content.

---

# 7.28 Adaptive Retrieval Depth

Retrieval depth should correspond to task complexity.

A simple request:

```text

"What is 2 + 2?"

```

requires almost no external context.

A complex architecture question may require:

```text

Current Architecture

\+

Relevant Chapters

\+

Previous Decisions

\+

Implementation Experience

\+

Current Code

\+

Active Goals

```

Therefore:

```text

Task Complexity

      │

      ▼

Retrieval Depth

      │

      ▼

Context Size

```

The Context Engine should avoid maximizing retrieval merely because more information is available.

---

# 7.29 Planner Interaction

The Planning Engine may request specific information needed to develop or execute a plan.

For example:

```text

Planner

  │

  ▼

Required Information

  │

  ├── Architecture

  ├── Available Tools

  ├── Previous Attempts

  └── Constraints

  │

  ▼

Context Engine

  │

  ▼

Relevant Context

  │

  ▼

Planner

```

The Planner determines **what information it needs**.

The Context Engine determines **how that information is assembled**.

This separation prevents the planner from becoming coupled to every storage mechanism.

---

# 7.30 Context Refresh

Context may need to be rebuilt when new information arrives.

Examples include:

* tool results

* user corrections

* new observations

* planner changes

* external events

* updated goals

* detected contradictions

```text

Active Context

      │

      ▼

New Information

      │

      ▼

Context Refresh

      │

      ▼

Updated Active Context

```

The engine should update only affected portions where practical rather than rebuilding everything unnecessarily.

---

# 7.31 Context Feedback Loop

Context quality affects outcomes.

Outcomes affect experience.

Experience can influence future context selection.

```text

Context

   │

   ▼

Reasoning

   │

   ▼

Action

   │

   ▼

Outcome

   │

   ▼

Experience

   │

   ▼

Learning

   │

   ▼

Future Context Selection

```

This creates a feedback loop in which successful retrieval patterns can become more effective over time.

The Learning Engine owns learning.

The Context Engine consumes the resulting improvements.

# 7.32 Explainability

Context construction should be inspectable.

Developers should be able to determine:

* what was retrieved

* what was rejected

* why information was selected

* ranking scores

* source provenance

* confidence values

* token allocation

* compression operations

* conflicts detected

* final context composition

* retrieval latency

A conceptual diagnostic view might be:

```text

Context Decision



Memory #184

Relevance: 0.94

Confidence: 0.87

Importance: 0.91

Included: Yes



Memory #932

Relevance: 0.42

Confidence: 0.91

Importance: 0.20

Included: No

Reason: Low task relevance

```

This transparency is essential for debugging and improving retrieval behavior.

# 7.33 Context Validation

Before the context is provided to a reasoning system, it should be validated.

Validation may check:

* token limits

* required fields

* source integrity

* duplicate content

* unresolved conflicts

* missing critical requirements

* malformed data

* stale information

* prohibited information

* context ordering

Conceptually:

```text

Assembled Context

       │

       ▼

Validation

       │

   ┌───┴───┐

   │       │

 Valid   Invalid

   │       │

   ▼       ▼

Reason   Repair

```

A context package should never be assumed valid merely because retrieval succeeded.

# 7.34 Context and Safety

The Context Engine must respect system-level information boundaries.

Not all available information is necessarily eligible for every context.

Context selection may therefore be constrained by:

* permissions

* data sensitivity

* user authorization

* tool scope

* security policies

* system constraints

The Context Engine enforces context eligibility provided by the appropriate security and trust systems.

It does not independently redefine security policy.

---

# 7.35 Context Persistence

The Context Engine does not automatically persist its working context.

When a cognitive operation completes:

```text

Active Context

      │

      ├── Temporary → Discard

      │

      └── Valuable → Evaluate for Promotion

```

Promotion may result in:

* memory

* experience

* knowledge

* skill updates

* conversation checkpoint

* task state

The destination is determined by the subsystem responsible for that information.

This establishes the architectural rule:

> **Context is temporary unless explicitly promoted.**

---

# 7.36 Context Checkpoints

Long-running conversations and tasks may require checkpoints.

A checkpoint captures enough state to reconstruct useful continuity later.

It may contain:

```text

Checkpoint



Conversation State

Active Goals

Task State

Important Decisions

Open Questions

Relevant References

Compressed History

Critical Constraints

```

A checkpoint is not necessarily permanent memory.

It is a recovery and continuity mechanism.

The Memory or Task systems may subsequently decide whether portions of the checkpoint deserve longer-term persistence.

---

# 7.37 Context and Long-Running Tasks

A task may outlive a conversation.

```text

Conversation

     │

     ▼

Task Created

     │

     ▼

Conversation Ends

     │

     ▼

Task Continues

     │

     ├── New Context

     ├── New Observations

     ├── Updated Plan

     └── Updated State

```

The Context Engine reconstructs task-specific context when the task resumes.

This prevents an old conversation context from becoming an indefinitely growing task context.

# 7.39 Performance and Caching

Context assembly may become computationally expensive.

Future implementations may therefore support:

* retrieval caching

* context caching

* semantic cache keys

* reusable context fragments

* incremental context updates

* prefetching

* asynchronous retrieval

Caching must respect information lifetime and validity.

A cached context fragment must never be assumed to remain correct indefinitely.

# 7.40 Failure Handling

Context failures should degrade gracefully.

### Memory Unavailable

```text

Memory

  ↓

Failure

  ↓

Use Available Knowledge / Conversation

```

### Knowledge Retrieval Failure

```text

Knowledge

  ↓

Failure

  ↓

Use Existing Context

```

### Compression Failure

```text

Compression

  ↓

Failure

  ↓

Reduce Candidate Set

  ↓

Continue

```

### Budget Overflow

```text

Context Too Large

      ↓

Re-rank

      ↓

Remove Low Priority

      ↓

Compress

      ↓

Validate

```

The Context Engine should prefer degraded but valid operation over silent context corruption.

# 7.42 Design Principles

The Context Engine follows these architectural principles:

1\. **Context is temporary.**

2\. **Memory remains independent.**

3\. **Experience remains independent.**

4\. **Knowledge remains independently owned.**

5\. **Context is assembled on demand.**

6\. **Retrieval is requirement-driven.**

7\. **Relevant information is prioritized over abundant information.**

8\. **Context sources retain provenance.**

9\. **Conflicting information is not silently discarded.**

10\. **Token budgets are explicit.**

11\. **Compression preserves meaning.**

12\. **Working context is disposable.**

13\. **Conversation continuity does not require replaying all history.**

14\. **Context construction is observable.**

15\. **Context selection is constrained by security and authorization.**

16\. **Long-running tasks receive reconstructed context rather than infinite accumulated context.**

---

# 7.43 Architectural Invariants

### Invariant 1 — The Context Engine does not own permanent memory.

It consumes memory; it does not become memory.

### Invariant 2 — The Context Engine does not own knowledge.

Knowledge remains authoritative within its source system.

### Invariant 3 — The Context Engine does not own experience.

Experience is supplied by the Experience Engine.

### Invariant 4 — Context is bounded.

No cognitive operation may assume unlimited context capacity.

### Invariant 5 — Context selection is deliberate.

Information should enter context because it has a reason to be there.

### Invariant 6 — Temporary information expires.

Working context does not become permanent automatically.

### Invariant 7 — Provenance is preserved.

The system should be able to identify where important context originated.

### Invariant 8 — Compression must not fabricate information.

Summarization is not permission to invent missing facts.

### Invariant 9 — Context construction is observable.

The architecture must support inspection of context decisions.

### Invariant 10 — Context may be rebuilt.

The active context is a derived state and can be reconstructed from authoritative sources.

# 7.44 Relationship to Chapter 06

The Conversation Engine and Context Engine have deliberately different responsibilities.

```text

Conversation Engine

        │

        │ "What does this interaction require?"

        ▼

Context Engine

        │

        │ "What information satisfies those requirements?"

        ▼

Memory / Experience / Knowledge / Goals / Tasks

        │

        ▼

Assembled Context

        │

        ▼

Conversation Engine

        │

        ▼

Planning / Reasoning / Execution

```

The boundary is:

> **Conversation Engine coordinates the interaction.**

> **Context Engine constructs the information environment required by that interaction.**

This prevents the two systems from becoming redundant.

```text
     ↓

Validation

     ↓

Active Context

     ↓

Reasoning

```

The architectural distinction is fundamental:

```text

Memory      → What exists

Knowledge   → What is known

Experience  → What happened

Planning    → What should happen

Context     → What matters now

```

The Context Engine does not attempt to remember everything.

It determines what deserves attention **now**.

By keeping context temporary, bounded, relevant, observable, and reconstructable, RoBoT can operate across conversations and tasks that greatly exceed the context window of any individual model.

This provides the foundation for scalable reasoning, long-running tasks, adaptive retrieval, multimodal cognition, and lifelong learning.

> **Memory gives RoBoT access to its past. Context determines which part of that past enters the present.**
