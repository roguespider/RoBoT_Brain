# Chapter 28 - Developer Interface and Control Plane

**Architecture Version:** v0.0.2.1  
**Document Role:** Normative architectural chapter  
**v0.0.2.1 Focus:** Inspection and control interfaces, read/write separation, permissions, safe mutation, audit and recovery  


## 28.1 Overview

The Developer Interface and Control Plane provides humans and authorized AI contributors with tools to inspect, manage, debug, and maintain RoBoT.

A cognitive architecture requires more than code.

It requires visibility and control.

The Control Plane answers:

- What is RoBoT doing?
- Why did it do it?
- What systems are active?
- What memories influenced a decision?
- Which workers are running?
- What changed recently?
- Is the system healthy?

The Control Plane does not create intelligence.

It manages intelligence.

# 28.2 Design Philosophy

The Control Plane follows five principles.

## Visibility Before Modification

A developer should understand the system before changing it.

Bad:

```text id="x2m8lf"
Open database

Change values manually

Hope nothing breaks
```

Good:

```text id="4p9h7a"
Inspect

↓

Understand

↓

Modify through controlled interface

↓

Verify
```

---

## Control Without Direct Manipulation

The Control Plane provides safe operations.

Instead of:

```sql
UPDATE memories SET confidence = 1.0;
```

Use:

```text id="h7f4cm"
Memory Management Tool

Action:
Adjust confidence

Reason:
Verified source update

Audit:
Created
```

---

## Everything Leaves a Trace

Every administrative action produces:

- actor identity
- timestamp
- reason
- affected system
- before state
- after state

# 28.21 Summary

The Developer Interface and Control Plane gives RoBoT maintainability as the architecture grows.

Without a control plane:

- debugging becomes guesswork
- changes become risky
- learning becomes invisible

With a control plane:

- systems become understandable
- changes become controlled
- failures become traceable
- evolution becomes manageable

The guiding principle:

```text id="d7x3wp"
A complex intelligence system

must have a clear window,

a safe control panel,

and a complete history.
```

The Control Plane is the bridge between human understanding and machine complexity.

With Chapter 28 added, the architecture now has the missing "operator layer." The earlier chapters describe the brain, and this chapter adds the instrument panel and diagnostic equipment.

## Final v0.0.2.1 Integration Contract

This chapter is normative within the v0.0.2.1 architecture. Its subject matter must integrate with the architecture-wide contract in `FINAL_ARCHITECTURE_SPEC.md`.

### Required cross-boundary behavior

1. **Ownership:** This chapter defines or refines responsibilities without taking ownership of another subsystem's durable state.
2. **Lifecycle:** Every state or operation introduced here has explicit creation, active, completion, failure, retention, expiration, or archival behavior as applicable.
3. **Identity:** Operations retain the correlation and entity identifiers needed to reconstruct their relationship to conversations, goals, plans, actions, executions, experiences, events, and configuration changes.
4. **Evidence:** Observed information, inferred information, candidate changes, evaluated information, and promoted knowledge remain distinguishable.
5. **Uncertainty:** Missing information, contradiction, confidence, and unresolved conditions are represented rather than silently collapsed.
6. **Failure:** Errors, retries, partial completion, cancellation, recovery, and terminal failure remain observable.
7. **Model independence:** This chapter must not require persistent state to live inside a particular model, prompt format, inference runtime, or context window.
8. **Controlled effects:** Any external or privileged effect must pass through the appropriate authorization, execution, validation, and audit boundary.
9. **Observability:** Important state transitions and outcomes must produce structured evidence suitable for monitoring and reconstruction.
10. **Versioning:** Changes to contracts, schemas, events, or lifecycle semantics require explicit versioning and compatibility handling.
11. **GUI/control-plane integration:** When this chapter exposes functionality to humans, the GUI communicates through the Developer Interface and Control Plane. It must not directly mutate subsystem storage or bypass security.
12. **Testing:** The chapter's architectural guarantees must be testable through the testing architecture defined in Chapter 30.

### Chapter-specific v0.0.2.1 focus

**GUI, developer interface, control plane, read/write separation, inspection, safe mutation, permissions, audit, recovery and operational workflows.**

### Definition of done

This chapter is considered v0.0.2.1-complete only when its responsibilities, interfaces, lifecycle, failure behavior, security boundary, persistence implications, observability, and testing requirements can be identified without relying on undocumented assumptions.

## GUI operation classes

### Observe

Read-only inspection of:

- system health
- engine status
- active conversations
- context composition
- memory and knowledge
- experiences
- goals/tasks/plans
- executions
- tools
- workers
- models
- configuration
- events
- traces
- audit records

### Operate

Controlled actions such as:

- pause/resume workers
- cancel an execution
- stop a task
- retry an eligible operation
- approve a pending change
- start a permitted workflow
- initiate recovery

### Configure

Controlled mutation of:

- runtime profiles
- model selection
- worker parameters
- interface settings
- retention policies
- tool permissions

Configuration mutation is validated and audited.

### Dangerous operations

Destructive or high-risk operations require explicit privilege and, where policy requires it, confirmation.

Examples:

- deleting persistent knowledge
- purging event history
- revoking a critical capability
- changing security policy
- replacing production configuration
- initiating destructive recovery

The GUI must never expose a privileged operation merely because a backend endpoint exists.

## GUI state model

The GUI should consume normalized control-plane state rather than constructing its own independent cognitive state.

A GUI view may cache display data, but that cache is not authoritative memory.

GUI sessions therefore have:

- session identity
- authenticated actor identity
- permissions
- correlation identity
- view state
- expiration

The GUI must tolerate subsystem restarts and reconnect by reconstructing its view from authoritative state.

## GUI observability

Every mutation initiated through the GUI should be traceable to:

- actor
- GUI session
- command
- target
- timestamp
- authorization decision
- correlation ID
- result

Sensitive values are redacted before presentation or logging.
