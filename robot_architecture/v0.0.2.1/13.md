# 13. Tool Engine

## 13.1 Purpose

The Tool Engine provides RoBoT with controlled access to capabilities outside the core cognitive architecture.

A language model can reason about files, repositories, databases, APIs, programs, devices, and external services, but reasoning alone does not provide access to them.

The Tool Engine bridges that boundary.

It exposes capabilities through structured contracts that define:

* what a tool does

* what inputs it accepts

* what outputs it produces

* what permissions it requires

* what resources it consumes

* what risks it presents

* how it reports errors

* how it is discovered

* how it is versioned

The Tool Engine is intentionally model-agnostic.

The LLM does not directly call operating-system APIs, external services, databases, or hardware.

Instead:

```text

Model / Reasoning

       │

       ▼

Planning

       │

       ▼

Execution

       │

       ▼

Tool Engine

       │

       ▼

Capability

       │

       ▼

External World

```

This creates a controlled boundary between cognition and external effects.

The Tool Engine provides **capabilities**.

The Execution Engine performs **execution**.

The Planning Engine determines **intent and strategy**.

These responsibilities must remain separate.

---

# 13.2 Architectural Role

The Tool Engine is a capability layer rather than a planning or execution layer.

Its primary question is:

> **What capabilities are available to RoBoT, and what contract governs each capability?**

The Tool Engine does not decide:

* what the user wants

* which objective should be pursued

* which strategy is best

* which task should execute next

* whether a goal has been achieved

Those decisions belong to the Planning Engine.

The Tool Engine does not own:

* execution scheduling

* global execution budgets

* execution state

* retries across an entire plan

* checkpoints for plans

* cancellation of complete execution graphs

Those responsibilities belong to the Execution Engine.

The Tool Engine provides the controlled capability implementation used by execution.

# 13.4 Core Principles

The Tool Engine follows several architectural principles.

## Capability Based

Capabilities are exposed through stable identities.

Examples:

```text

filesystem.read

filesystem.write

memory.search

memory.store

github.search

github.commit

cargo.build

cargo.test

sqlite.query

web.search

speech.transcribe

image.generate

```

The capability identity should remain stable even if its underlying implementation changes.

---

## Strong Contracts

Every tool exposes a defined contract.

A contract describes:

* identity

* purpose

* version

* parameters

* parameter schema

* return schema

* permissions

* resource requirements

* supported execution modes

* failure behavior

* compatibility requirements

The contract allows the rest of RoBoT to reason about the capability without depending on its implementation details.

---

## Implementation Independence

A capability should not be permanently tied to one implementation.

For example:

```text

filesystem.read

       │

       ├── local filesystem adapter

       ├── sandboxed filesystem adapter

       └── remote filesystem adapter

```

The Execution Engine requests the capability.

The Tool Engine resolves that capability to an available implementation.

This allows tools to be replaced without redesigning the Planning Engine.

---

## Least Privilege

Tools receive only the permissions required to perform their declared capability.

A tool should never receive broad access merely because it is convenient.

---

## Isolation

Tool failures must remain isolated from the rest of RoBoT whenever possible.

A crashing external tool should produce a structured failure rather than terminating the cognitive system.

---

## Observability

Every invocation produces measurable telemetry.

Tool usage should never disappear into an opaque execution path.

---

## Replaceability

A tool implementation should be replaceable without requiring changes throughout the architecture.

---

# 13.5 Tool Categories

RoBoT separates capabilities into several categories.

## 1. Internal Tools

Capabilities implemented directly within RoBoT.

Examples:

* memory.search

* memory.store

* experience.search

* context.compress

* graph.query

* learning.update

* planning.inspect

* database.query

These operate against controlled RoBoT subsystems.

---

## 2. Local System Tools

Capabilities that interact with the local operating environment.

Examples:

* filesystem.read

* filesystem.write

* filesystem.create

* filesystem.delete

* process.spawn

* process.inspect

* cargo.build

* cargo.test

* cargo.check

* rustfmt

* clippy

* git.status

* git.diff

* git.commit

Local tools are subject to permissions and execution-time safety controls.

---

## 3. MCP Tools

Model Context Protocol servers provide externally implemented capabilities.

Examples include:

* GitHub

* databases

* documentation systems

* IDE integrations

* custom services

* enterprise systems

MCP is treated as a transport and capability integration mechanism rather than a special category of privileged tool.

---

## 4. External Services

Capabilities provided through external APIs.

Examples:

* web search

* weather

* maps

* translation

* OCR

* image generation

* speech synthesis

* speech recognition

* cloud storage

* email

* calendar

External service failures must be represented as structured tool failures.

---

## 5. Hardware Capabilities

Capabilities that interact with physical devices.

Examples:

* microphone

* camera

* speakers

* GPU

* USB devices

* sensors

Hardware access requires explicit capability and permission management.

# 13.6 Tool Identity

Every capability receives a stable identity.

A recommended format is:

```text

<namespace>.<capability>

```

Examples:

```text

filesystem.read

filesystem.write

github.search

github.repository.read

cargo.build

memory.search

memory.store

speech.transcribe

```

The identity represents the capability rather than the implementation.

```text
├── filesystem.write
```

The registry supports:

* registration

* availability checks

* health state

The registry prevents capabilities from being hard-coded throughout the architecture.

# 13.9 Capability Discovery

The Tool Engine supports capability discovery.

A planning request may specify:

```text

Required Capability:



filesystem.read

```

The registry resolves available implementations.

```text

filesystem.read

      │

      ▼

Capability Registry

      │

      ├── Local Adapter

      ├── Sandboxed Adapter

      └── Remote Adapter

```

The selected implementation must satisfy the required contract.

---

# 13.10 Capability Negotiation

Some capabilities may expose different levels of functionality.

Example:

```text

filesystem.read

```

may support:

```text

read file

read range

stream file

read metadata

```

The Tool Engine may negotiate the appropriate capability level based on the execution request and implementation support.

This allows RoBoT to remain compatible with different tool versions and providers.

---

# 13.11 Tool Contract

A tool contract defines the boundary between RoBoT and the implementation.

Conceptually:

```text

ToolContract

{

    identity

    version

    input\_schema

    output\_schema

    permissions

    resource\_requirements

    failure\_contract

    execution\_constraints

}

```

A valid implementation must satisfy the declared contract.

Contract validation prevents incompatible tools from being silently substituted.

---

# 13.12 Parameter Validation

Before a tool implementation receives input, the Tool Engine validates:

* required parameters

* parameter types

* ranges

* enumerations

* string constraints

* path constraints

* schema requirements

* capability-specific restrictions

Invalid requests must fail before reaching the implementation.

Example:

```text

Tool Request

     │

     ▼

Schema Validation

     │

     ├── Invalid ──► Reject

     │

     └── Valid

           │

           ▼

       Permission Check

```

---

# 13.13 Permission Model

Every capability declares required permissions.

Example:

```text

filesystem.read

    └── filesystem.read



filesystem.write

    └── filesystem.write



github.commit

    ├── network.github

    └── repository.write



terminal.execute

    └── process.execute

```

Permissions should be evaluated before execution.

Possible approval levels include:

* automatic

* session-approved

* user-approved

* administrator-approved

The exact approval requirement depends on risk and system configuration.

---

# 13.14 Permission Scoping

Permissions should be scoped as narrowly as possible.

For example:

```text

Bad:



filesystem.write = entire filesystem





Better:



filesystem.write

    root = project\_directory

```

Likewise:

```text

github.commit

    repository = authorized\_repository

```

This prevents a capability from receiving unnecessary authority.

---

# 13.15 Tool Invocation Boundary

Tool invocation follows a defined boundary:

```text

Execution Engine

       │

       ▼

Tool Engine

       │

       ▼

Validate Contract

       │

       ▼

Validate Parameters

       │

       ▼

Check Permissions

       │

       ▼

Resolve Implementation

       │

       ▼

Invoke Capability

       │

       ▼

Normalize Result

       │

       ▼

Return to Execution Engine

```

The Tool Engine should not bypass this boundary.

---

# 13.16 Relationship With Execution Engine

The Execution Engine owns execution mechanics.

The Tool Engine owns capability implementations.

The distinction is:

| Responsibility | Execution Engine | Tool Engine |

| ------------------------ | ------------------- | ------------------------------------- |

| Schedule actions | Yes | No |

| Manage execution graph | Yes | No |

| Manage plan budgets | Yes | No |

| Cancel execution | Yes | No |

| Retry action | Yes | Tool may define retry characteristics |

| Provide capability | No | Yes |

| Validate tool contract | No | Yes |

| Resolve implementation | No | Yes |

| Enforce tool permissions | Coordinates | Yes |

| Invoke implementation | Through Tool Engine | Yes |

| Normalize tool result | Consumes | Provides |

| Track tool health | Consumes | Yes |

This separation prevents Chapter 12 and Chapter 13 from becoming duplicate execution systems.

# 13.18 Structured Results

All capabilities return normalized results.

```text

ToolResult

{

    success

    status

    message

    data

    artifacts

    warnings

    error

    metadata

    metrics

}

```

The implementation may produce arbitrary internal formats.

The Tool Engine adapts those formats to the declared contract.

This prevents the rest of RoBoT from becoming dependent on raw tool-specific output.

Some tools produce artifacts rather than simple data.

Examples:

* generated files

* images

* audio

* repositories

* database changes

* compiled binaries

* reports

Artifacts should be represented explicitly.

```text

Artifact

{

    id

    type

    location

    size

    checksum

    metadata

}

```

This allows downstream systems to reference outputs without embedding large objects directly into execution state.

# 13.20 Streaming

Some capabilities produce continuous output.

Examples:

* compiler output

* transcription

* downloads

* indexing

* model inference

* long-running analysis

Streaming follows a common event model:

```text

Started

   │

   ▼

Progress

   │

   ▼

Partial Output

   │

   ▼

Progress

   │

   ▼

Completed

```

Streaming events may be consumed by the Execution Engine and optionally surfaced through the Conversation Engine.

# 13.21 Asynchronous Tools

Some capabilities may continue beyond the lifetime of a single invocation.

Examples:

* repository indexing

* large document processing

* embedding generation

* remote jobs

* long-running analysis

These capabilities return a job reference.

```text

Tool Request

     │

     ▼

Job Created

     │

     ▼

job\_id

     │

     ▼

Execution Engine

     │

     ▼

Monitor Job

```

The Execution Engine remains responsible for the lifecycle of the execution job.

The Tool Engine provides the capability interface.

---

# 13.22 Parallel Capability Use

Capabilities may declare whether concurrent invocation is supported.

```text

supports\_parallel = true

```

However, capability-level support does not automatically authorize parallel execution.

The Execution Engine determines whether parallel execution is appropriate based on:

* plan dependencies

* resource limits

* execution budgets

* permissions

* shared state

* capability restrictions

The Tool Engine reports capability constraints.

The Execution Engine makes the scheduling decision.

---

# 13.23 Retry Characteristics

Tools may declare whether failures are potentially retryable.

Example:

```text

RetryPolicy

{

    retryable\_errors

    maximum\_attempts

    backoff\_strategy

}

```

The Tool Engine identifies the characteristics of a capability failure.

The Execution Engine decides whether and when to retry the action as part of the execution lifecycle.

This keeps retry scheduling out of the Tool Engine while preserving tool-specific knowledge about retryability.

---

# 13.24 Timeouts

Tools declare execution characteristics such as expected or maximum duration.

Example:

```text

Tool:

cargo.build



Expected:

10-120 seconds



Maximum:

300 seconds

```

The Execution Engine enforces the actual execution deadline.

The Tool Engine provides the capability's declared constraints.

---

* resource consumption

A capability may transition through:

```text
    │

    ▼

Degraded

    │

    ▼

    │

    │
```

# 13.26 Tool Versioning

Tools are versioned independently from the core architecture.

Example:

```text

    v2

```

Version metadata allows RoBoT to:

* detect incompatible changes

* select compatible implementations

* migrate capabilities

* preserve reproducibility

* diagnose version-specific failures

The capability identity should remain stable where semantics remain compatible.

MCP is integrated through the Tool Engine rather than directly into the Planner.

```text

MCP Server

    │

    ▼

MCP Client

    │

    ▼

MCP Adapter

    │

    ▼

Capability Registration

    │

    ▼

```

The MCP adapter translates MCP-specific behavior into RoBoT's internal tool contract.

This creates a clean abstraction:

```text

Planner

   │

   ▼

Capability

   │

   ▼

Tool Engine

   │

   ├── Local Adapter

   ├── MCP Adapter

   ├── API Adapter

   └── Hardware Adapter

```

The Planner does not need to know whether a capability is implemented through MCP, Rust, HTTP, or another mechanism.

# 13.29 MCP Server Management

The Tool Engine may manage MCP server lifecycle operations such as:

* discovery

* startup

* connection

* capability enumeration

* health checks

* shutdown

* reconnection

* failure isolation

An MCP server must not receive privileges beyond the capabilities it explicitly exposes and the permissions granted to those capabilities.

---

# 13.30 Local Plugin System

RoBoT may support local plugins for capabilities that should remain outside the core binary.

Plugins may expose:

* manifests

* capabilities

* versions

* permissions

* dependencies

* lifecycle hooks

A plugin should be treated as an untrusted capability provider unless explicitly trusted.

Plugin isolation is therefore important for future extensibility.

---

# 13.31 Sandboxing

Capabilities that execute arbitrary code or interact with sensitive resources should be isolated whenever possible.

Candidates include:

* Python execution

* shell commands

* external executables

* third-party plugins

* downloaded tools

* untrusted code

Sandbox restrictions may include:

* filesystem access

* network access

* CPU

* memory

* execution time

* process creation

Sandbox policy belongs to the security architecture, while the Tool Engine applies the capability-specific sandbox requirements.

---

# 13.32 Dry Run

Capabilities that support potentially destructive operations should expose a dry-run mode where practical.

Example:

```text

filesystem.delete

```

may support:

```text

dry\_run = true

```

Result:

```text

Would delete:

    file\_a

    file\_b

    file\_c

```

Dry-run capability allows Planning and Execution systems to validate intended effects before committing them.

---

# 13.33 Side Effects

Tools must declare whether they produce external side effects.

Examples:

```text

filesystem.read

    side\_effect = false



filesystem.write

    side\_effect = true



github.search

    side\_effect = false



github.commit

    side\_effect = true

```

Side-effect metadata allows the Execution and Safety systems to apply appropriate controls.

---

# 13.34 Idempotency

Tools should declare whether an operation is idempotent where practical.

Example:

```text

filesystem.read

    idempotent = true



filesystem.write

    depends\_on\_mode



github.commit

    idempotent = false

```

This information helps the Execution Engine determine whether retries are safe.

---

# 13.35 Security Model

The Tool Engine follows a zero-trust capability model.

Every invocation should:

1\. Validate the request.

2\. Validate parameters.

3\. Verify capability availability.

4\. Check permissions.

5\. Apply execution restrictions.

6\. Invoke the implementation.

7\. Validate the result.

8\. Record the invocation.

No tool should be trusted merely because it is registered.

Registration establishes availability.

Permission establishes authority.

Execution establishes the actual operation.

---

# 13.39 Memory Integration

Tool output should not automatically become permanent memory.

Temporary tool output belongs to execution state or context.

Only information that provides lasting value should be promoted into Memory.

Examples appropriate for memory:

* discovered project conventions

* stable repository structure

* persistent API behavior

* reusable workflow knowledge

* durable configuration information

Examples generally unsuitable for permanent memory:

* temporary logs

* compiler output

* duplicate search results

* transient errors

* raw API responses with no lasting value

Memory curation remains the responsibility of the Memory architecture.

# 13.41 Capability Scoring

Tool selection may use historical performance.

Conceptually:

```text

Capability Score =

    reliability

  + availability

  + expected quality

  + historical success

  - latency

  - cost

  - risk

```

The exact scoring algorithm belongs to the Planning and Learning architecture.

The Tool Engine provides the factual capability metadata and telemetry required to support that decision.

This prevents the Tool Engine from becoming responsible for strategic tool selection.

---

# 13.42 Tool Composition

Simple capabilities may be combined into higher-level composite capabilities.

Example:

```text

repository.analyze

       │

       ├── repository.read

       ├── filesystem.read

       ├── cargo.check

       └── test.run

```

Composite tools must preserve the same capability contract and execution boundaries.

However, complex strategic workflows should remain plans rather than being hidden inside composite tools.

This prevents the Tool Engine from becoming an alternate Planning Engine.

---

# 13.43 Tool Testing

Every capability should support testing at multiple levels.

### Contract Testing

Does the implementation satisfy its declared interface?

### Permission Testing

Does it reject unauthorized requests?

### Failure Testing

Does it return structured errors?

### Timeout Testing

Does it terminate correctly?

### Isolation Testing

Does a failure remain contained?

### Result Testing

Does output conform to its schema?

### Integration Testing

Does the capability work correctly through the Tool Engine?

Tool reliability should be measurable before the capability becomes trusted for autonomous operation.

# 13.46 Design Principles

The Tool Engine follows these architectural principles:

### 1. Capabilities, Not Strategies

Tools provide capabilities.

They do not determine objectives or strategies.

### 2. Contracts Are Explicit

Every capability has a defined interface.

### 3. Permissions Are Mandatory

Registration does not imply authority.

### 4. Implementations Are Replaceable

Capabilities should not depend on a single implementation.

### 5. Results Are Structured

Raw tool-specific formats remain behind the Tool Engine boundary.

### 6. Failures Are Isolated

A tool failure must not become a system failure.

### 7. Side Effects Are Declared

Tools must identify operations that modify external state.

### 8. Observability Is Mandatory

Every meaningful invocation produces telemetry.

### 9. Security Is Defense in Depth

Validation, permission checks, isolation, and execution controls work together.

### 10. Execution Remains Separate

The Execution Engine owns execution lifecycle and scheduling.

### 11. Planning Remains Separate

The Planning Engine owns strategic decisions.

### 12. Learning Is Feedback

Historical tool performance improves future capability selection.

### 13. Tool Output Is Not Automatically Memory

Only useful information should be promoted into long-term knowledge.

```text
              ┌──────────┼──────────┐

              ▼          ▼          ▼

           Planning   Experience  Learning

```

This creates a clean separation of concerns:

> **Planning chooses the strategy.**

> **Execution performs the strategy.**

> **Tools provide the capabilities.**

> **The world produces the results.**

> **Experience records what happened.**

> **Learning improves what happens next.**

# 13.48 Integration Summary

The Tool Engine is RoBoT's controlled capability boundary to the external world.

It provides the mechanisms through which RoBoT can interact with files, programs, repositories, databases, APIs, MCP servers, hardware, and other external systems without allowing those systems to become directly coupled to the cognitive architecture.

The Tool Engine does not plan.

It does not own execution scheduling.

It does not determine user intent.

It provides capabilities through explicit contracts, validates requests, resolves implementations, enforces capability-level permissions, normalizes results, manages tool lifecycle, monitors capability health, and records telemetry.

This separation creates three distinct architectural layers:

```text

Planning

   │

   │ Strategy

   ▼

Execution

   │

   │ Controlled Action

   ▼

Tools

   │

   │ Capability

   ▼

World

```

The resulting feedback loop is:

```text

Intent

  │

  ▼

Planning

  │

  ▼

Execution

  │

  ▼

Tool

  │

  ▼

World

  │

  ▼

Observation

  │

  ├──────────────► Experience

  │

  └──────────────► Learning

                         │

                         ▼

                    Better Planning

```

The Tool Engine therefore serves as the **capability infrastructure of RoBoT**.

It gives the cognitive architecture controlled hands without giving those hands control over the mind.

That distinction is fundamental to keeping RoBoT modular, secure, observable, replaceable, and capable of scaling from local Rust modules and MCP integrations into a much larger distributed capability ecosystem.

## Final v0.0.2.1 Integration Contract

This chapter is normative within the v0.0.2.1 architecture. Its subject matter must integrate with the architecture-wide contract in `FINAL_ARCHITECTURE_SPEC.md`.

### Required cross-boundary behavior

1. **Ownership:** This chapter defines or refines responsibilities without taking ownership of another subsystem's durable state.
2. **Lifecycle:** Every state or operation introduced here has explicit creation, active, completion, failure, retention, expiration, or archival behavior as applicable.
3. **Identity:** Operations retain the correlation and entity identifiers needed to reconstruct their relationship to conversations, goals, plans, actions, executions, experiences, events, and configuration changes.
4. **Evidence:** Observed information, inferred information, candidate changes, evaluated information, and promoted knowledge remain distinguishable.
5. **Uncertainty:** Missing information, contradiction, confidence, and unresolved conditions are represented rather than silently collapsed.
6. **Failure:** Errors, retries, partial completion, cancellation, recovery, and terminal failure remain observable.
7. **Model independence:** This chapter must not require persistent state to live inside a particular model, prompt format, inference runtime, or context window.
8. **Controlled effects:** Any external or privileged effect must pass through the appropriate authorization, execution, validation, and audit boundary.
9. **Observability:** Important state transitions and outcomes must produce structured evidence suitable for monitoring and reconstruction.
10. **Versioning:** Changes to contracts, schemas, events, or lifecycle semantics require explicit versioning and compatibility handling.
11. **GUI/control-plane integration:** When this chapter exposes functionality to humans, the GUI communicates through the Developer Interface and Control Plane. It must not directly mutate subsystem storage or bypass security.
12. **Testing:** The chapter's architectural guarantees must be testable through the testing architecture defined in Chapter 30.
