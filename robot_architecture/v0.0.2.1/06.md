\# Chapter 06 — Conversation Engine



\*\*Version:\*\* v0.0.2

\*\*Status:\*\* Architectural Specification



\---



\## 6.1 Purpose



The Conversation Engine is RoBoT's \*\*interaction orchestration layer\*\*.



Its purpose is to transform an incoming interaction into a structured cognitive process and coordinate the systems required to produce an appropriate response or action.



The Conversation Engine does \*\*not\*\* contain the intelligence of RoBoT.



It does not own:



\* long-term memory

\* knowledge

\* experience

\* planning

\* learning

\* tool implementations

\* reasoning models

\* permanent user information



Instead, it coordinates these capabilities.



The engine provides the controlled path through which an interaction moves between external interfaces and RoBoT's cognitive architecture.



```text

External Interaction

&#x20;       │

&#x20;       ▼

Conversation Engine

&#x20;       │

&#x20;       ├── Input Normalization

&#x20;       ├── Conversation State

&#x20;       ├── Intent / Goal Routing

&#x20;       ├── Context Request

&#x20;       ├── Cognitive Coordination

&#x20;       ├── Action Coordination

&#x20;       ├── Response Construction

&#x20;       └── Outcome Recording

&#x20;       │

&#x20;       ▼

External Response / Action

```



The fundamental architectural principle is:



> \*\*The Conversation Engine coordinates cognition; it does not own cognition.\*\*



This distinction prevents the Conversation Engine from becoming a monolithic subsystem that accumulates memory, planning, reasoning, tool logic, and business rules over time.



\---

&#x20;           │              │

\# 6.3 Core Design Principles



\## 6.3.1 Conversation Is a Process



A conversation is not simply a sequence of prompts sent to an LLM.



Each interaction is processed through a lifecycle.



```text

Input

&#x20; ↓

Normalize

&#x20; ↓

Understand

&#x20; ↓

Establish State

&#x20; ↓

Assemble Context

&#x20; ↓

Determine Required Cognitive Work

&#x20; ↓

Plan / Reason / Retrieve / Act

&#x20; ↓

Construct Response

&#x20; ↓

Evaluate Outcome

&#x20; ↓

Record Experience

&#x20; ↓

Promote Relevant Learning

```



Not every interaction requires every stage.



For example, a simple conversational response may require no tools, planning, or long-term memory retrieval.



A complex task may require all of them.



The Conversation Engine determines \*\*which stages are required\*\*, while specialized systems perform the work.



\---



\## 6.3.2 The LLM Is a Component



An LLM is not the architectural center of RoBoT.



The model provides capabilities such as:



\* language understanding

\* language generation

\* reasoning

\* classification

\* summarization

\* transformation



RoBoT provides the surrounding architecture:



\* persistent knowledge

\* memory

\* experience

\* goals

\* state

\* planning

\* tools

\* execution

\* learning

\* identity

\* constraints



This allows the underlying model to be replaced, upgraded, specialized, or distributed without redesigning the overall cognitive architecture.



\---



\## 6.3.3 Context Is Requested, Not Accumulated



The Conversation Engine must never assume that the entire history of a conversation belongs in every inference request.



Instead, it requests the information required for the current cognitive operation.



```text

Current Interaction

&#x20;       │

&#x20;       ▼

Conversation State

&#x20;       │

&#x20;       ▼

Context Requirements

&#x20;       │

&#x20;       ├── Working Context

&#x20;       ├── Relevant Memory

&#x20;       ├── Relevant Knowledge

&#x20;       ├── Relevant Experience

&#x20;       ├── Active Goals

&#x20;       └── Planning State

&#x20;       │

&#x20;       ▼

Context Assembly

&#x20;       │

&#x20;       ▼

Cognitive Processing

```



This prevents conversation history from becoming an uncontrolled source of context growth.



Context management itself belongs to the Context Engine.



The Conversation Engine determines \*\*what context is required\*\*, while the Context Engine determines \*\*how that context is assembled and managed\*\*.



\---



\## 6.3.4 State and Knowledge Have Different Lifetimes



Conversation state is temporary.



Knowledge and memory may be persistent.



The Conversation Engine maintains the state necessary to operate an active interaction, while persistent information is delegated to the appropriate subsystem.



```text

Conversation State

&#x20;     │

&#x20;     │ temporary

&#x20;     ▼

Conversation Engine



Persistent Information

&#x20;     │

&#x20;     ├── Memory

&#x20;     ├── Knowledge

&#x20;     ├── Experience

&#x20;     └── Learned Skills

```



This separation prevents temporary conversational information from automatically becoming permanent knowledge.



\---



\## 6.3.5 Events Provide Loose Coupling



Important changes within the conversation lifecycle are represented as structured events.



Examples include:



```text

ConversationStarted

InputReceived

InputNormalized

IntentDetected

GoalIdentified

ContextRequested

ContextAssembled

MemoryRetrieved

ExperienceRetrieved

PlanRequested

ToolRequested

ToolCompleted

ToolFailed

ReasoningStarted

ReasoningCompleted

ResponseGenerated

OutcomeEvaluated

ExperienceRecorded

LearningTriggered

ConversationCompleted

```



Events allow subsystems to observe activity without requiring the Conversation Engine to directly control every implementation.

\# 6.4 Responsibilities



The Conversation Engine owns orchestration responsibilities.



Its primary responsibilities are:



1\. Receive interactions.

2\. Normalize interaction input.

3\. Establish or update conversation state.

4\. Coordinate intent and goal analysis.

5\. Determine required cognitive operations.

6\. Request relevant context.

7\. Coordinate planning and reasoning.

8\. Coordinate tool and skill execution.

9\. Assemble response inputs.

10\. Produce the interaction result.

11\. Record outcome information.

12\. Emit lifecycle events.



The Conversation Engine does \*\*not\*\* directly own the implementation of these capabilities.



For example:



```text

Conversation Engine

&#x20;      │

&#x20;      ├── requests memory

&#x20;      │        └── Memory Engine owns retrieval

&#x20;      │

&#x20;      ├── requests planning

&#x20;      │        └── Planning Engine owns planning

&#x20;      │

&#x20;      ├── requests execution

&#x20;      │        └── Execution / Tool systems own execution

&#x20;      │

&#x20;      └── requests learning

&#x20;               └── Learning Engine owns learning

```



This ownership model keeps subsystem boundaries explicit.

\# 6.5 Interaction Input



All external interactions are converted into a normalized internal representation.



An interaction may originate from:



\* text

\* speech

\* image input

\* video input

\* files

\* application interfaces

\* APIs

\* automated processes

\* internal system events



The Conversation Engine should not require every interface to understand the internal cognitive architecture.



Instead:



```text

External Input

&#x20;     ↓

Input Adapter

&#x20;     ↓

ConversationInput

&#x20;     ↓

Conversation Engine

```



A normalized `ConversationInput` may contain:



```text

ConversationInput



InputID

ConversationID

SessionID

Source

Timestamp

Content

Attachments

Modality

Metadata

CorrelationID

```



The exact implementation may evolve, but the architectural requirement remains:



> External interfaces must be normalized before entering the cognitive lifecycle.



\---



\# 6.6 Conversation Understanding



After normalization, the engine coordinates interpretation of the interaction.



Understanding may identify:



\* probable intent

\* entities

\* topic

\* requested action

\* goals

\* ambiguity

\* constraints

\* urgency

\* required capabilities

\* relevant prior state

\* possible tool requirements



Multiple intents may exist within one interaction.



For example:



```text

"Check my schedule, find a restaurant near the meeting,

and remind me tomorrow."



```



This may contain:



```text

Intent 1 → retrieve schedule

Intent 2 → search restaurants

Intent 3 → create reminder

```



The Conversation Engine therefore treats intent as potentially \*\*composite\*\*, rather than forcing every interaction into one category.



\---



\# 6.7 Goal and Task Coordination



Conversation often creates or modifies goals.



The Conversation Engine coordinates the relationship between the current interaction and active goals.



```text

User Input

&#x20;   │

&#x20;   ▼

Intent

&#x20;   │

&#x20;   ▼

Goal Relationship

&#x20;   │

&#x20;   ├── New Goal

&#x20;   ├── Existing Goal

&#x20;   ├── Goal Modification

&#x20;   ├── Goal Completion

&#x20;   └── No Goal

```



The Conversation Engine does not become the permanent owner of goals.



Instead, it communicates goal changes to the appropriate goal or planning subsystem.



This distinction becomes important for long-running tasks.



A conversation may end while a task continues.



Therefore:



> \*\*Conversation lifetime and task lifetime are not necessarily the same.\*\*



\---



\# 6.8 Context Coordination



The Conversation Engine determines what information is required to handle the current interaction.



Possible requirements include:



```text

Current Conversation

&#x20;      │

&#x20;      ├── Working Context

&#x20;      ├── Relevant Memory

&#x20;      ├── Relevant Knowledge

&#x20;      ├── Relevant Experience

&#x20;      ├── Active Goals

&#x20;      ├── Planner State

&#x20;      └── Retrieved External Information

```



The engine sends these requirements to the appropriate systems.



The Context Engine then assembles the usable cognitive context.



This creates a clean division:



| Responsibility                 | Owner               |

| ------------------------------ | ------------------- |

| Determine context requirements | Conversation Engine |

| Retrieve relevant information  | Specialized systems |

| Assemble usable context        | Context Engine      |

| Maintain persistent memory     | Memory Engine       |

| Maintain experience            | Experience Engine   |

| Maintain knowledge             | Knowledge systems   |

| Maintain planning state        | Planning Engine     |

\# 6.9 Cognitive Cycle Coordination



The Conversation Engine coordinates the cognitive cycle required for an interaction.



A simple request may follow:



```text

Input

&#x20;↓

Context

&#x20;↓

Reasoning

&#x20;↓

Response

```



A complex request may follow:



```text

Input

&#x20;↓

Context

&#x20;↓

Planning

&#x20;↓

Memory Retrieval

&#x20;↓

Knowledge Retrieval

&#x20;↓

Tool Execution

&#x20;↓

Result Evaluation

&#x20;↓

Additional Planning

&#x20;↓

Reasoning

&#x20;↓

Response

```



The engine must therefore support \*\*iterative cognitive cycles\*\* rather than assuming that every interaction is a single pass.



For example:



```text

Plan

&#x20;↓

Execute

&#x20;↓

Observe Result

&#x20;↓

Update State

&#x20;↓

Re-plan

&#x20;↓

Execute

```



This provides the foundation for multi-step tasks and long-running workflows.

\# 6.10 Tool and Skill Coordination



When an interaction requires an external action, the Conversation Engine coordinates the request.



Possible execution targets include:



\* tools

\* skills

\* databases

\* filesystem operations

\* APIs

\* MCP services

\* code execution

\* external applications



The Conversation Engine should not contain tool-specific implementation logic.



Instead:



```text

Conversation Engine

&#x20;       │

&#x20;       ▼

Action Request

&#x20;       │

&#x20;       ▼

Execution / Tool System

&#x20;       │

&#x20;       ▼

Action Result

&#x20;       │

&#x20;       ▼

Conversation Engine

```



The returned result becomes new information available to the cognitive cycle.



This allows tool execution to become part of reasoning rather than an isolated side operation.

\# 6.11 Response Construction



The final response is constructed from the current cognitive result.



Inputs may include:



\* reasoning results

\* retrieved knowledge

\* memory

\* experience

\* tool results

\* planning results

\* task state

\* constraints

\* safety requirements

\* requested response format



```text

Cognitive Results

&#x20;      │

&#x20;      ├── Reasoning

&#x20;      ├── Knowledge

&#x20;      ├── Memory

&#x20;      ├── Experience

&#x20;      │

&#x20;      │

&#x20;      ▼

```



The response should represent the \*\*current best result of the cognitive process\*\*, rather than simply exposing raw outputs from individual subsystems.

\# 6.15 Conversation Modes



The Conversation Engine may operate across multiple interaction modes.



\## Chat Mode



General conversational interaction.



\## Question Answering



Retrieve relevant knowledge and construct an answer.



\## Planning Mode



Develop or modify a multi-step plan.



\## Coding Mode



Coordinate coding-related reasoning, context, tools, and execution.



\## Creative Mode



Generate or transform creative content.



\## Research Mode



Coordinate retrieval, analysis, comparison, and synthesis.



\## Learning Mode



Teach, explain, test, or reinforce knowledge.



\## Reflection Mode



Perform internally initiated evaluation or analysis.



\## Task Execution Mode



Coordinate a persistent task that may continue beyond a single interaction.



These modes are \*\*operational behaviors\*\*, not separate engines.



A single conversation may transition between modes.



For example:



```text

Chat

&#x20;↓

Question

&#x20;↓

Planning

&#x20;↓

Task Execution

&#x20;↓

Reflection

&#x20;↓

Chat

```

\# 6.17 Error Handling and Recovery



The Conversation Engine must be designed for partial failure.



A failure in one subsystem should not automatically terminate the conversation.



Examples:



\### Memory Failure



```text

Memory Request

&#x20;     ↓

Failure

&#x20;     ↓

Continue With Available Context

&#x20;     ↓

Record Failure

```



\### Tool Failure



```text

Tool Request

&#x20;     ↓

Failure

&#x20;     ↓

Retry / Alternate Action

&#x20;     ↓

Fallback

&#x20;     ↓

Report Result

```



\### Planning Failure



```text

Planner

&#x20; ↓

Failure

&#x20; ↓

Simplify Task

&#x20; ↓

Direct Reasoning

```



\### Model Failure



```text

Inference

&#x20;  ↓

Failure

&#x20;  ↓

Retry

&#x20;  ↓

Alternate Model / Provider

&#x20;  ↓

Graceful Degradation

```



Recovery policy should remain explicit and observable.



The goal is not to hide failures.



The goal is to prevent recoverable failures from unnecessarily collapsing the entire cognitive process.

\# 6.18 Safety and Trust Boundary



The Conversation Engine is part of RoBoT's trust boundary but is not itself the complete safety system.



Before actions are executed, appropriate policy and safety controls may evaluate:



\* authorization

\* permissions

\* tool access

\* user intent

\* action risk

\* data sensitivity

\* execution constraints



Conceptually:



```text

Conversation Request

&#x20;       │

&#x20;       ▼

Action Decision

&#x20;       │

&#x20;       ▼

Safety / Trust Evaluation

&#x20;       │

&#x20;  ┌────┴────┐

&#x20;  │         │

Allowed    Blocked

&#x20;  │         │

&#x20;  ▼         ▼

Execute    Explain

```



The Conversation Engine coordinates this process but does not replace the dedicated Security and Trust Architecture.

\# 6.19 Experience and Learning



The completion of a conversation does not automatically mean that everything discussed should become permanent knowledge.



Instead, the outcome is evaluated.



```text

Conversation Outcome

&#x20;       │

&#x20;       ▼

Experience Evaluation

&#x20;       │

&#x20;       ├── No Significant Learning

&#x20;       │

&#x20;       ├── Record Experience

&#x20;       │

&#x20;       ├── Update Existing Knowledge

&#x20;       │

&#x20;       ├── Create New Memory

&#x20;       │

&#x20;       ├── Modify Relationships

&#x20;       │

&#x20;       └── Trigger Learning

```



This distinction is critical.



\*\*Conversation produces information.\*\*



\*\*Experience determines what happened.\*\*



\*\*Learning determines what should change.\*\*



\*\*Memory determines what should persist.\*\*



The Conversation Engine coordinates these transitions but does not own them.

\# 6.20 Information Ownership



The following ownership model prevents architectural overlap.



| Information                | Primary Owner           | Conversation Engine Role |

| -------------------------- | ----------------------- | ------------------------ |

| Active conversation state  | Conversation Engine     | Own                      |

| Temporary interaction data | Conversation Engine     | Own                      |

| Working context            | Context Engine          | Request                  |

| Long-term memory           | Memory Engine           | Request                  |

| Knowledge                  | Knowledge System        | Request                  |

| Experience                 | Experience Engine       | Record / Request         |

| Goals                      | Goal / Planning System  | Coordinate               |

| Plans                      | Planning Engine         | Coordinate               |

| Tool implementations       | Tool / Execution System | Invoke                   |

| MCP services               | MCP / Tool System       | Invoke                   |

| Learning                   | Learning Engine         | Trigger                  |

| Persistent skills          | Skill System            | Invoke / Coordinate      |

| Model inference            | LLM Interface           | Request                  |

| Safety policy              | Security / Trust System | Enforce                  |



The Conversation Engine should resist absorbing responsibilities that belong elsewhere.



This is one of its most important architectural constraints.

\# 6.21 Context Window Management



The Conversation Engine must operate independently of any particular model context-window size.



It should never assume:



```text

Conversation History = Model Context

```



Instead:



```text

Conversation History

&#x20;       │

&#x20;       ▼

Context Requirements

&#x20;       │

&#x20;       ▼

Context Engine

&#x20;       │

&#x20;       ├── Relevant History

&#x20;       ├── Working Context

&#x20;       ├── Memory

&#x20;       ├── Knowledge

&#x20;       ├── Experience

&#x20;       └── Goals

&#x20;       │

&#x20;       ▼

Context Compression / Selection

&#x20;       │

&#x20;       ▼

Model Context

```



This allows RoBoT to continue operating as conversations become arbitrarily long.



The architecture manages information relevance rather than simply increasing prompt size.

\# 6.22 Long-Running Conversations and Tasks



A conversation and a task may have different lifetimes.



For example:



```text

Conversation

&#x20;  │

&#x20;  ├── Start Task

&#x20;  │

&#x20;  └── End Conversation

&#x20;           │

&#x20;           ▼

&#x20;      Task Continues

&#x20;           │

&#x20;           ├── Execute

&#x20;           ├── Observe

&#x20;           ├── Re-plan

&#x20;           └── Complete

```



This distinction enables future support for:



\* long-running workflows

\* background execution

\* scheduled operations

\* persistent tasks

\* asynchronous tools

\* autonomous task continuation



The Conversation Engine provides the interaction boundary while other systems maintain the continuing task state.

\* outcome status

\* resource usage

\* correlation identifiers



Observability is required not only for debugging but also for understanding how RoBoT's cognitive architecture behaves over time.



A system that cannot explain the path taken by an interaction is difficult to improve safely.

\# 6.25 Extensibility



The Conversation Engine is intentionally designed around stable interfaces rather than implementation-specific assumptions.



Future capabilities may include:



\* multi-agent interaction

\* multiple simultaneous tasks

\* persistent autonomous workflows

\* voice-first interaction

\* multimodal conversations

\* distributed model execution

\* model routing

\* asynchronous cognition

\* background reflection

\* collaborative planning

\* autonomous task continuation

\* dynamic skill selection



These capabilities should be introduced by extending the orchestration model rather than turning the Conversation Engine into a monolithic implementation.

\# 6.26 Architectural Invariants



The following rules define the boundaries of the Conversation Engine.



\### Invariant 1 — The Conversation Engine does not own long-term memory.



Persistent information belongs to persistent information systems.



\### Invariant 2 — The Conversation Engine does not own planning.



Planning belongs to the Planning Engine.



\### Invariant 3 — The Conversation Engine does not own learning.



Learning belongs to the Learning Engine.



\### Invariant 4 — The Conversation Engine does not implement tools.



Tools and execution systems own their implementations.



\### Invariant 5 — The Conversation Engine does not treat the LLM as the system itself.



The model is an inference component within the larger architecture.



\### Invariant 6 — Conversation state is temporary unless explicitly promoted.



Information must earn persistence.



\### Invariant 7 — Context is selected by relevance.



The engine must not blindly replay complete history.



\### Invariant 8 — Failures are observable.



Recovery must not erase evidence that a subsystem failed.



\### Invariant 9 — Conversation and task lifetimes may differ.



Ending a conversation must not automatically terminate a persistent task.



\### Invariant 10 — Subsystems retain ownership of their domains.



The Conversation Engine coordinates them without absorbing their responsibilities.

\# 6.28 Future Evolution



The architecture intentionally leaves room for more advanced cognitive behavior.



Future versions may introduce:



\### Concurrent Cognitive Operations



Multiple retrieval, planning, or tool operations may execute simultaneously.



\### Dynamic Model Routing



Different models may be selected according to task requirements.



\### Recursive Task Execution



A task may generate subtasks that are independently planned and executed.



\### Background Cognition



Reflection, maintenance, consolidation, and learning may occur independently of active conversation.



\### Multi-Agent Coordination



Multiple specialized agents may participate in a single cognitive process.



\### Persistent Task Sessions



Tasks may remain active across multiple conversations.



\### Distributed Cognition



Different cognitive services may execute across multiple machines or models.



These capabilities are compatible with the architecture because the Conversation Engine is defined around \*\*coordination and lifecycle management\*\*, rather than a fixed implementation.

\# 6.29 Summary



The Conversation Engine is the \*\*interaction orchestration layer of RoBoT\*\*.



It transforms external interaction into a structured cognitive lifecycle:



```text

Input

&#x20;↓

Normalization

&#x20;↓

Understanding

&#x20;↓

State Update

&#x20;↓

Context Requirements

&#x20;↓

Context Assembly

&#x20;↓

Planning / Reasoning / Retrieval

&#x20;↓

Execution

&#x20;↓

Observation

&#x20;↓

Response Construction

&#x20;↓

Outcome Evaluation

&#x20;↓

Experience

&#x20;↓

Learning / Memory Promotion

```



The Conversation Engine does not attempt to become the brain of RoBoT.



It provides the pathways through which the specialized cognitive systems cooperate.



Its most important architectural responsibilities are therefore:



\* coordinate interaction

\* maintain temporary conversation state

\* determine cognitive requirements

\* request relevant context

\* coordinate planning and reasoning

\* coordinate execution

\* construct responses

\* emit lifecycle events

\* preserve observability

\* coordinate experience and learning



The resulting architecture separates \*\*conversation from cognition, cognition from storage, and storage from learning\*\*.



That separation allows RoBoT to evolve without turning every new capability into another responsibility of the Conversation Engine.



> \*\*The Conversation Engine is the conductor of the cognitive process, not the orchestra itself.\*\*
