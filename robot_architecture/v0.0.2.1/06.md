# Chapter 06 — Conversation Engine

**Version:** v0.0.2.1
**Status:** Architectural Specification
**Architecture:** RoBoT Cognitive Architecture

---

## 6.1 Purpose

The Conversation Engine is RoBoT's **interaction orchestration system**.

Its purpose is to transform external interaction into a controlled cognitive lifecycle and coordinate the systems required to understand, process, execute, and respond to that interaction.

The Conversation Engine does **not** contain the intelligence of RoBoT.

It does not own:

- Long-term memory
- Permanent knowledge
- Experience
- Learning
- Planning logic
- Tool implementations
- Execution implementations
- Model implementations
- Knowledge storage
- Retrieval implementations
- Persistent user information

Instead, it coordinates the systems that own those responsibilities.

The fundamental architectural principle is:

> **The Conversation Engine coordinates cognition; it does not own cognition.**

This distinction prevents the Conversation Engine from becoming a monolithic subsystem in which memory, reasoning, planning, tools, state, and business logic gradually accumulate.

---

## 6.2 Architectural Position

The Conversation Engine sits between external interaction and the internal cognitive architecture.

```text
┌──────────────────────────────────────────────┐
│              External Interfaces             │
│                                              │

│  Files │ Events │ Automation │ Hardware      │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│              Conversation Engine             │
│                                              │
│  Input Normalization                         │
│  Conversation State                          │
│  Intent / Goal Coordination                  │
│  Context Requirements                        │
│  Cognitive Cycle Coordination                │
│  Interaction Lifecycle                       │
│  Response Coordination                       │
│  Outcome Recording                           │
│  Event Emission                              │
└───────────┬──────────────┬───────────────────┘
            │              │

```

The Conversation Engine therefore acts as a **coordination boundary**.

Each subsystem remains responsible for its own domain.

## 6.3 Core Architectural Principles

### 6.3.1 Conversation Is a Cognitive Process

A conversation is not simply a sequence of prompts sent to a language model.

Each interaction represents a lifecycle.

```text
External Interaction
        │
        ▼
Normalize
        │
        ▼
Establish Conversation State
        │
        ▼
Understand Interaction
        │
        ▼
Determine Goals / Tasks
        │
        ▼
Determine Context Requirements
        │
        ▼
Assemble Cognitive Input
        │
        ▼
Reason / Retrieve / Plan / Act
        │
        ▼
Evaluate Result
        │
        ▼
Construct Response
        │
        ▼
Record Outcome
        │
        ▼
Trigger Experience / Learning
```

Not every interaction requires every stage.

A simple question may require only understanding, context retrieval, reasoning, and response generation.

A complex task may require memory, planning, tools, execution, observation, evaluation, experience recording, and learning.

The Conversation Engine determines **which stages are required**.

Specialized systems perform the actual work.

---

### 6.3.2 The Language Model Is a Component

The language model is not the architectural center of RoBoT.

A model may provide capabilities including:

- Language understanding
- Language generation
- Reasoning
- Classification
- Summarization
- Transformation
- Planning assistance
- Extraction

RoBoT provides the architecture surrounding those capabilities:

- Persistent knowledge
- Memory
- Experience
- Goals
- State
- Context
- Planning
- Execution
- Tools
- Learning
- Identity
- Constraints
- Provenance
- Confidence
- Observability

The underlying model may therefore be replaced, upgraded, specialized, distributed, or supplemented without requiring the entire cognitive architecture to be redesigned.

---

### 6.3.3 Context Is Requested, Not Accumulated

The Conversation Engine must never assume that the complete history of a conversation belongs in every inference request.

Instead, it determines what information the current operation requires and requests that information from the appropriate systems.

```text
Current Interaction
        │
        ▼
Conversation State
        │
        ▼
Context Requirements
        │
        ├── Current Task
        ├── Relevant Conversation State
        ├── Relevant Memory
        ├── Relevant Knowledge
        ├── Relevant Experience
        ├── Active Goals
        ├── Planning State
        └── Required Constraints
        │
        ▼
Context Engine
        │
        ▼
Cognitive Context
```

The Conversation Engine determines:

> **What context is required?**

The Context Engine determines:

> **How that context is assembled, prioritized, bounded, and delivered.**

This distinction prevents the Conversation Engine from becoming responsible for context management.

---

### 6.3.4 State and Knowledge Have Different Lifetimes

Conversation state is temporary.

Knowledge may be persistent.

Experience may persist independently of conversation state.

Working context may exist for only a single cognitive cycle.

The Conversation Engine therefore manages interaction state without automatically promoting that state into permanent storage.

```text
Temporary
────────────────────────────

Conversation State
Working Interaction State
Current Task State
Current Response State

────────────────────────────
Persistent / Long-Lived

Memory
Knowledge
Experience
Skills
Learned Models
User Knowledge
Strategic Knowledge
```

Temporary information must not become permanent merely because it appeared in a conversation.

Promotion into persistent systems requires explicit ownership and appropriate evaluation.

---

### 6.3.5 Subsystem Ownership Is Explicit

The Conversation Engine coordinates capabilities but does not absorb ownership of those capabilities.

```text
Conversation Engine
        │
        ├── requests context
        │       └── Context Engine owns context assembly
        │
        ├── requests memory
        │       └── Memory Engine owns memory
        │
        ├── requests planning
        │       └── Planning Engine owns planning
        │
        ├── requests execution
        │       └── Execution Engine owns execution
        │
        ├── requests tools
        │       └── Tool Engine owns tool capabilities
        │
        ├── records experience
        │       └── Experience Engine owns experience
        │
        └── triggers learning
                └── Learning Engine owns learning
```

The Conversation Engine coordinates these operations without reimplementing them.

---

### 6.3.6 Structured Contracts Define Boundaries

Communication between the Conversation Engine and other systems must use the canonical data contracts defined by the architecture.

Examples include:

- `ConversationInput`
- `ConversationState`
- `ContextRequest`
- `Context`
- `Goal`
- `Plan`
- `ActionRequest`
- `ExecutionResult`
- `Observation`
- `ExperienceRecord`
- `LearningUpdate`
- `ConversationResult`

Subsystems must not rely on undocumented internal structures.

This preserves:

- Interoperability
- Versionability
- Validation
- Traceability
- Testing
- Replacement of implementations

## 6.4 Conversation Lifecycle

A complete interaction lifecycle can be represented as:

```text
1. Interaction Received
          │
          ▼
2. Input Normalized
          │
          ▼
3. Conversation State Updated
          │
          ▼
4. Interaction Understood
          │
          ▼
5. Goals / Tasks Identified
          │
          ▼
6. Context Requirements Determined
          │
          ▼
7. Context Requested
          │
          ▼
8. Cognitive Work Determined
          │
          ▼
9. Planning / Retrieval / Reasoning / Action
          │
          ▼
10. Result Observed
          │
          ▼
11. Outcome Evaluated
          │
          ▼
12. Response Constructed
          │
          ▼
13. Experience Recorded
          │
          ▼
14. Learning Triggered When Appropriate
          │
          ▼
15. Conversation State Finalized
```

This lifecycle is logical rather than necessarily sequential.

Some operations may occur concurrently.

Some may repeat.

Some may be skipped.

Some tasks may return to an earlier stage when new information becomes available.

For example:

```text
Plan
 │
 ▼
Execute
 │
 ▼
Observe
 │
 ▼
Failure
 │
 ▼
Replan
 │
 ▼
Execute
```

The Conversation Engine coordinates these transitions while specialized engines own the underlying operations.

```text

      │
      ▼

      │
      ▼

      │
```

```text

```

## 6.6 Conversation Identity

Every interaction must be associated with sufficient identity information to establish its relationship to the surrounding activity.

At minimum, the architecture should distinguish:

```text
ConversationID
SessionID
InputID
CorrelationID
```

These identifiers serve different purposes.

### ConversationID

Identifies the logical conversation.

### SessionID

Identifies a particular runtime interaction session.

### InputID

Identifies an individual incoming interaction.

### CorrelationID

Connects related operations across subsystem boundaries.

For complex tasks, additional identifiers may exist:

```text
TaskID
GoalID
PlanID
ActionID
ExecutionID
ExperienceID
```

This identity structure allows RoBoT to reconstruct what happened without relying solely on natural-language conversation history.

## 6.7 Conversation State

Conversation state represents the temporary operational state required to coordinate an active interaction.

It may contain:

```text
ConversationState

ConversationID
SessionID

CurrentInput
ActiveGoals
ActiveTasks

CurrentTurn
CurrentStage

PendingOperations
ActivePlans
PendingActions

RequiredContext
CurrentContextReference

LastResult
CurrentStatus

CreatedAt
UpdatedAt
```

Conversation state is **not long-term memory**.

It exists to coordinate the current interaction lifecycle.

When information becomes valuable beyond the active interaction, the appropriate subsystem determines whether it should be preserved.

## 6.8 Understanding the Interaction

After normalization, the Conversation Engine coordinates interpretation of the interaction.

Potential information includes:

- Intent
- Entities
- Topic
- Requested action
- Goals
- Constraints
- Ambiguity
- Urgency
- Required capabilities
- Relevant state
- Potential tool requirements
- Potential knowledge requirements

Intent may be composite.

For example:

```text
"Check my schedule, find a restaurant near the meeting,
and remind me tomorrow."
```

may contain:

```text
Intent 1 → Retrieve schedule
Intent 2 → Find restaurant
Intent 3 → Create reminder
```

The Conversation Engine therefore must not force every interaction into a single intent category.

## 6.9 Goal and Task Coordination

An interaction may:

- Create a goal
- Modify an existing goal
- Complete a goal
- Suspend a goal
- Resume a goal
- Create one or more tasks
- Modify task requirements
- Cancel a task
- Provide information relevant to an existing task

The Conversation Engine coordinates these relationships.

```text
Interaction
     │
     ▼
Intent
     │
     ▼
Goal Relationship
     │
     ├── New Goal
     ├── Existing Goal
     ├── Goal Modification
     ├── Goal Completion
     └── No Goal Change
     │
     ▼
Task Determination
```

Goal ownership belongs to the appropriate planning and goal-management systems.

The Conversation Engine maintains the relationship between the current interaction and those systems.

## 6.12 Planning and Reasoning Coordination

The Conversation Engine may request planning or reasoning but does not own their implementations.

```text
Conversation Engine
        │
        ├──────────────► Planning Engine
        │
        └──────────────► Reasoning System
```

Planning determines:

> **What should be done?**

Reasoning determines:

> **What can be concluded, inferred, or decided from the available information?**

Execution determines:

> **How is an approved action performed?**

The Conversation Engine coordinates these systems without collapsing their responsibilities into a single process.

---

## 6.13 Action Coordination

When a task requires external action, the Conversation Engine coordinates the transition from cognitive decision to operational execution.

```text
Decision
   │
   ▼
ActionRequest
   │
   ▼
Execution Engine
   │
   ▼
Tool / Skill / External System
   │
   ▼
ExecutionResult
   │
   ▼
Observation
   │
   ▼
Conversation Engine
```

The Conversation Engine must not directly execute tools merely because it is coordinating the interaction.

Execution remains owned by the Execution Engine and Tool Engine.

## 6.14 Response Construction

A response is the final interaction representation produced after the required cognitive work has completed.

The Conversation Engine coordinates response construction from:

- Current interaction
- Conversation state
- Relevant context
- Cognitive results
- Execution results
- Constraints
- Safety requirements
- Communication requirements

A response may contain:

```text
ConversationResult

ResultID
ConversationID
CorrelationID

Content
Attachments
Actions

Status
Confidence

Provenance
References

CreatedAt
```

A response may also indicate that no final response can yet be produced because:

- More information is required
- A task is still running
- A tool failed
- User clarification is required
- A policy constraint prevented execution
- The task was abandoned
- A result requires human approval

The architecture therefore treats response generation as a **stateful outcome**, not merely text generation.

---

## 6.15 Outcome Evaluation

After execution or reasoning, the result must be evaluated.

Evaluation may determine:

- Whether the requested objective was achieved
- Whether the result is complete
- Whether the result is reliable
- Whether additional action is required
- Whether the user should be asked for clarification
- Whether the operation failed
- Whether the result produced useful experience
- Whether learning should be triggered

```text
Expected Outcome
       │
       ▼
Actual Outcome
       │
       ▼
Evaluation
       │
       ├── Success
       ├── Partial Success
       ├── Failure
       ├── Uncertain
       └── Requires Follow-up
```

Outcome evaluation should rely on evidence where possible rather than assuming that completion of an action means successful completion of the user's objective.

---

## 6.16 Experience Recording

Conversation results may generate experience.

However, the Conversation Engine does not decide that every conversation should become permanent experience.

Instead, it emits the information required by the Experience Engine.

```text
Interaction
     │
     ▼
Outcome
     │
     ▼
Experience Candidate
     │
     ▼
Experience Engine
     │
     ├── Evaluate
     ├── Normalize
     ├── Score
     ├── Store
     └── Reject / Discard
```

This preserves the architectural distinction:

> **Conversation produces events and outcomes. Experience determines what operational knowledge is worth preserving.**

## 6.17 Learning Coordination

The Conversation Engine may trigger learning opportunities but does not perform learning.

Potential triggers include:

- Successful task completion
- Repeated failure
- New operational pattern
- Unexpected result
- User correction
- Improved strategy
- Tool behavior change
- Discovery of a new relationship
- Repeated successful execution

```text
Conversation Outcome
        │
        ▼
Learning Candidate
        │
        ▼
Learning Engine
        │
        ├── Evaluate
        ├── Generalize
        ├── Update Knowledge
        ├── Update Skills
        └── Reject
```

Learning must remain separate from conversation orchestration.

## 6.19 Error Handling

The Conversation Engine must treat failure as a normal architectural condition rather than an exceptional state that terminates the entire system by default.

Failures may occur during:

- Input normalization
- Context retrieval
- Memory retrieval
- Planning
- Reasoning
- Tool execution
- External services
- Response construction
- Outcome evaluation

The engine should classify failures according to their recoverability.

```text
Failure
  │
  ├── Recoverable
  │       │
  │       ├── Retry
  │       ├── Replan
  │       └── Request More Context
  │
  ├── User-Resolvable
  │       │
  │       └── Request Clarification
  │
  ├── External Failure
  │       │
  │       └── Report / Defer
  │
  └── Terminal Failure
          │
          └── Complete With Failure
```

A failed action must not automatically be interpreted as a failed conversation.

A failed plan must not necessarily terminate the goal.

A failed tool call may result in replanning.

This allows RoBoT to recover rather than simply collapse when one operation fails.

---

## 6.20 Conversation Suspension and Resumption

Complex tasks may continue beyond a single interaction.

The Conversation Engine must therefore support suspension and resumption.

A suspended interaction may preserve references to:

```text
ConversationID
GoalID
TaskID
PlanID
CurrentState
PendingOperations
RequiredContext
LastKnownOutcome
ResumeConditions
```

Persistent state should be stored by the appropriate persistence systems rather than relying on the Conversation Engine's in-memory state.

When resumed, the Conversation Engine reconstructs the required working state from authoritative sources.

This prevents process restarts from destroying long-running cognitive work.

---

## 6.21 Concurrency

Multiple operations may exist within a single conversation.

For example:

```text
User Request
     │
     ├── Retrieve Memory
     │
     ├── Query Knowledge
     │
     ├── Inspect Current State
     │
     └── Retrieve External Information
              │
              ▼
        Context Assembly
```

The Conversation Engine may coordinate concurrent operations when dependencies allow them.

Concurrency must not violate:

- Data ownership
- Contract guarantees
- Ordering requirements
- Causality
- Safety constraints
- Resource limits

The engine must preserve causal relationships even when operations execute concurrently.

---

## 6.22 Conversation Boundaries

The Conversation Engine must distinguish between:

### Interaction

A single incoming or outgoing exchange.

### Conversation

A logical sequence of related interactions.

### Session

A runtime execution period.

### Task

A unit of work associated with a goal.

### Goal

An intended outcome.

### Experience

A retained record of what happened and what was learned from it.

These concepts must not be collapsed into a single "conversation history" structure.

```text
Goal
 │
 ├── Task
 │    ├── Interaction
 │    ├── Plan
 │    ├── Action
 │    └── Result
 │
 └── Experience
```

This separation is essential for long-running autonomous operation.

---

## 6.23 Conversation History Is Not Memory

Conversation history may contain useful information.

That does not make conversation history equivalent to memory.

Conversation history answers:

> **What was said or what happened during this interaction sequence?**

Memory answers:

> **What information should remain available for future reasoning?**

Experience answers:

> **What happened during an operation, and what should RoBoT learn from it?**

Knowledge answers:

> **What does RoBoT currently believe to be true or useful?**

These systems may reference one another but must remain architecturally distinct.

---

## 6.24 Conversation State Is Not Identity

Conversation state must not be used as the authoritative representation of RoBoT's identity.

Identity, persistent user information, long-term preferences, learned capabilities, and strategic knowledge belong to persistent systems.

The Conversation Engine may request those resources when required.

It must not silently redefine them.

## 6.26 Security and Trust Boundaries

The Conversation Engine is a high-value coordination boundary.

It must not assume that every incoming instruction is trustworthy.

Inputs may originate from:

- Users
- Applications
- External systems
- Automated processes
- Tools
- Other agents
- Internal events

The engine must preserve provenance and pass appropriate trust information to downstream systems.

```text
Input
 │
 ▼
Identity
 │
 ▼
Source
 │
 ▼
Provenance
 │
 ▼
Policy / Constraint Evaluation
 │
 ▼
Cognitive Processing
```

The Conversation Engine coordinates policy checks but does not become the sole security subsystem.

Security decisions remain subject to the Security and Trust Architecture.

## 6.27 Human Intervention

Certain operations may require human intervention.

Examples include:

- High-impact actions
- Ambiguous authorization
- Irreversible operations
- Uncertain decisions
- Safety-sensitive actions
- Policy conflicts
- Explicit approval requirements

The Conversation Engine must support a state such as:

```text
AwaitingHumanApproval
```

rather than attempting to bypass the requirement.

```text
Decision
   │
   ▼
Approval Required
   │
   ▼
Await Human Input
   │
   ├── Approved ─────► Execute
   │
   ├── Rejected ─────► Cancel
   │
   └── Modified ─────► Replan
```

Human control therefore remains an architectural capability rather than an external workaround.

## 6.28 Implementation Independence

The Conversation Engine must remain independent from specific implementations of:

- Language models
- Databases
- Vector stores
- Graph stores
- Tool frameworks
- MCP implementations
- Operating systems
- User interfaces
- External APIs

Adapters may translate between architectural contracts and implementation-specific interfaces.

```text
Architectural Contract
        │
        ▼
Adapter
        │
        ▼
Implementation
```

This preserves the ability to replace infrastructure without redesigning the cognitive architecture.

---

## 6.29 Deterministic Coordination Where Possible

The Conversation Engine should use deterministic coordination logic wherever practical.

For example:

- Lifecycle transitions
- State management
- Event emission
- Contract validation
- Identifier propagation
- Retry policies
- Timeout handling
- Operation tracking
- Approval states

may be governed by explicit software logic.

Language models should not be required to perform basic orchestration that can be represented deterministically.

The model may recommend a path.

The architecture decides how that path is executed.

The Conversation Engine must support both:

### Interactive operation

```text
Human
 │
 ▼
Conversation
 │
 ▼
Cognitive Cycle
 │
 ▼
Response
```

### Autonomous operation

```text
Goal / Event
     │
     ▼
Conversation Lifecycle
     │
     ▼
Cognitive Cycle
     │
     ▼
Action
     │
     ▼
Observation
     │
     ▼

     │
```

This distinction is important.

RoBoT's cognitive architecture must not depend upon a human sending a new message for every cognitive cycle.

The Conversation Engine therefore acts as an **interaction and cognitive-cycle coordinator**, not merely a chatbot message handler.

## 6.31 Long-Running Conversations

A conversation may extend across:

- Multiple sessions
- Multiple runtime processes
- Multiple models
- Multiple environments
- Long periods of time

The Conversation Engine must therefore avoid making active process memory the authoritative source of long-term state.

Instead:

```text
Persistent Systems
       │
       ▼
Reconstruct Required State
       │
       ▼
Conversation Engine
       │
       ▼
Current Cognitive Cycle
```

This allows RoBoT to continue operating even when the runtime process, model, or interface changes.

## 6.32 Conversation Completion

A conversation does not necessarily end when a response is generated.

Completion may require:

- Delivering the response
- Recording the outcome
- Recording relevant experience
- Triggering learning
- Updating task state
- Updating goal state
- Releasing temporary resources
- Emitting completion events

A completed lifecycle may therefore be:

```text
Response Delivered
```

## 6.33 Architectural Invariants

The following invariants must remain true.

### Invariant 1

The Conversation Engine coordinates cognition but does not own cognition.

### Invariant 2

Conversation state is not long-term memory.

### Invariant 3

Conversation history is not equivalent to memory.

### Invariant 4

Context is requested according to cognitive requirements rather than accumulated indiscriminately.

### Invariant 5

Persistent knowledge must not be stored inside the Conversation Engine.

### Invariant 6

Experience must remain independent from conversation state.

### Invariant 7

Planning remains owned by the Planning Engine.

### Invariant 8

Execution remains owned by the Execution Engine.

### Invariant 9

Tool implementations remain owned by the Tool Engine.

### Invariant 10

Learning remains owned by the Learning Engine.

### Invariant 11

Subsystem communication must use defined architectural contracts.

### Invariant 12

Significant lifecycle transitions must remain observable.

### Invariant 13

Failures must be represented explicitly rather than hidden.

### Invariant 14

Long-running state must survive runtime boundaries through persistent systems.

### Invariant 15

The architecture must remain independent from any specific language model.

## 6.35 Summary

The Conversation Engine transforms external interaction into structured cognitive activity.

Its responsibility is orchestration.

It receives interaction, establishes temporary state, coordinates understanding, determines required context, invokes the appropriate cognitive and operational systems, evaluates results, constructs responses, and records the lifecycle needed by downstream systems.

It does not become the memory system.

It does not become the planning system.

It does not become the tool system.

It does not become the learning system.

It does not become the knowledge system.

It provides the controlled pathway through which those systems cooperate.

The architecture can therefore be summarized as:

```text
Interaction
     │
     ▼
Conversation Engine
     │
     ▼
Determine Cognitive Requirements
     │
     ▼
Request Context
     │
     ▼
Reason / Retrieve / Plan
     │
     ▼
Execute
     │
     ▼
Observe
     │
     ▼
Evaluate
     │
     ├──────────────► Experience
     │
     ├──────────────► Learning
     │
     └──────────────► State / Goal Updates
     │
     ▼
Construct Response
     │
     ▼
Complete or Continue
```

The defining principle of the Conversation Engine is therefore:

> **The Conversation Engine coordinates the cognitive lifecycle without becoming the cognitive architecture itself.**

This separation allows RoBoT to remain modular, observable, replaceable, persistent, and capable of operating across conversations, tasks, sessions, models, and environments without allowing interaction state to become the architecture's central storage mechanism.
